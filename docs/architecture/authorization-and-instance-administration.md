# Authorization and instance administration

Status: implemented

## Authentication and authorization

The sender/admin UI uses d6e-auth authorization-code OAuth. Access tokens are verified with RS256, issuer `d6e-auth`, and audience equal to `D6E_AUTH_CLIENT_ID`. Tokens remain inside an AES-GCM-encrypted, `HttpOnly`, `SameSite=Lax` server cookie.

d6e-auth proves identity, not envelope or organization access. Active organization memberships are fetched server-side. Suspended and closed organizations are rejected. A remembered organization cookie is display state only. Every query and mutation must match the authorized organization and object ID.

Recipient signing uses a separate, narrow capability link: high entropy, one recipient, stored as a hash, expiring, revocable, rate-limited, and unable to call operator APIs. A recipient does not need a d6e account by default. `GET /api/v1/signing/context` resolves only a bearer capability and is independent from browser OAuth organization state. Its D1 and PostgreSQL queries require a non-null future expiry, no revocation, a `pending` or `viewed` non-CC recipient, a `sent` or `in_progress` envelope, and a composite organization/envelope join. The response is an explicit allowlist that excludes organization identity, recipient email/name, and all token material; all inactive capability cases share one not-found shape.

The human `/s/<token>` route is a no-store, no-referrer exchange rather than the persistent signing page. After resolving current durable state, it seals the raw token into an AES-256-GCM `HttpOnly`, `SameSite=Lax` cookie and redirects to `/{locale}/sign`. HKDF-SHA-256 derives a recipient-session subkey from the deployment session master key, while versioned additional authenticated data prevents cross-purpose ciphertext reuse. Cookie lifetime is bounded by both the durable capability expiry and 30 days. The clean page decrypts server-side and re-resolves the database on every request; invalid or definitively inactive cookies are deleted, while transient persistence failures preserve them for retry. A failed or attacker-controlled new link never clears a previously valid session. Operator OAuth resolution is skipped for every recipient surface.

Recipient document reads resolve the pinned revision only from the active capability query. That query joins the tenant-scoped envelope to its `sent_commit_sha` revision command and requires the current immutable pointer to match the send pin; clients never submit an envelope ID, commit, object key, or path. The server reconstructs the content-addressed key, bounds the compressed archive and decoded gzip, recomputes SHA-256, requires Git HEAD to equal the send pin, and rechecks capability authorization immediately before disclosure. The browser renders a server-produced, sanitized CommonMark surface with GFM tables, strikethrough, autolinks, and task-list syntax. Raw HTML is disabled before conversion and the generated tree passes through an explicit allowlist that contains no image or active-content elements. Markdown images become inert alt-text notices, only absolute HTTPS and `mailto:` links remain interactive, HTTPS links open in a new tab with `noopener noreferrer`, and email links delegate to the user's mail handler without opening a blank tab. Bidi and other invisible formatting controls are replaced by visible `U+` markers in the formatted view while ordinary RTL text remains intact; an exact escaped Markdown-source tab remains available for verification. Rendering rejects more than fifty documents, more than 1 MiB of total source, a document over 512 KiB, a syntax tree deeper than 64 levels, or more than 50,000 syntax nodes. A global SvelteKit CSP additionally limits scripts, frames, objects, connections, forms, fonts, media, workers, and images to the minimum first-party surface. The bearer `GET /api/v1/signing/documents` endpoint returns the same allowlisted context and raw documents without organization, recipient identity, archive, digest, token, storage details, or generated HTML. This read path adds no view or audit mutation. Every later signing mutation decrypts the currently active cookie, re-resolves durable capability state, and treats submitted envelope and recipient IDs only as equality constraints, so replacing recipient A's cookie with recipient B's cannot authorize a stale A tab.

## Recipient decision commands

### Recording a view

The browser records a recipient view only through `POST /api/v1/signing/viewed` after the page is foreground-visible; link exchange, page load, prefetch, and document `GET`s remain read-only. The encrypted recipient cookie is the sole authority. Submitted envelope and recipient IDs are equality constraints against a fresh capability resolution, never alternate authority, and the endpoint accepts only exact same-origin requests. One idempotency key is scoped to the resolved recipient; a safe replay must match both the normalized request fingerprint and its stored audit evidence.

Publishing the first view changes the recipient from `pending` to `viewed`, may change its envelope from `sent` to `in_progress`, stores a durable command receipt, and appends a PII-free `recipient.viewed` audit event as one atomic database operation. PostgreSQL locks the envelope before the recipient and rechecks the capability, pinned revision, and audit head inside a transaction. D1 inserts the command through a trigger whose guarded recipient/envelope updates and audit insert roll back together on any failed predicate. A recipient already marked viewed without matching durable command and audit evidence is an integrity failure rather than an assumed replay. Revocation, expiry, recipient switching in another tab, audit-head races, and state drift are rechecked at publish and again before the response is disclosed.

### Recipient decline

Recipient decline is a separate explicit `POST /api/v1/signing/decline` confirmation, available only to an active signer or approver. It uses the encrypted recipient cookie as sole authority and treats submitted IDs only as equality constraints. Because success immediately makes the capability inactive, the decline store resolves identity by capability hash and owns both active publication and terminal replay verification; it does not depend on the active-access resolver after commit. One atomic publication marks the actor and envelope `declined`, revokes every other issued non-completed capability without changing sibling recipient statuses, terminally fails pending, blocked, and retryable-failed invitation intents, scrubs their sealed capability ciphertext, stores a durable command receipt, and appends one PII-free `recipient.declined` event. The receipt and audit payload contain the same sorted IDs of only the sibling capabilities actually revoked plus the stable `envelope_declined` reason; they never contain names, email addresses, capability hashes, ciphertext, key IDs, or outbox IDs. Existing delivered and permanent-failure evidence remains unchanged. D1 uses one command insert plus a rollback-on-failure trigger; PostgreSQL locks the envelope, every recipient, and every delivery row in stable order. A `processing` delivery lease observed before publication fences the entire decline with a retryable 409 before any mutation, so no new provider submission begins after the terminal commit; provider calls already accepted outside the database retain the documented at-least-once limitation. If that lease clears after a D1 trigger rollback but before failure classification, the safe fallback is an unavailable response with no mutation and no cookie clearing; retrying the command is safe. An exact evidence-checked replay succeeds after response loss only under the original idempotency key; version 1 receipts remain replayable after migration, while every new command uses version 2 revocation evidence. Version 2 replay also verifies the current sibling-revocation and scrubbed-delivery projection, so later authority drift fails closed. A fresh key presented after revocation receives the same opaque not-found outcome as other inactive capabilities. Mismatched tabs, inactive or non-actionable capabilities, key reuse, audit races, manifest drift, and partial terminal state fail closed. Successful and replayed browser responses replace the active capability cookie with a separately derived AES-GCM terminal-receipt cookie; cookie publication must succeed before the active cookie is removed, so a failed exchange remains safely replayable.

### Terminal decline receipt

The terminal decline receipt is a read-only authorization boundary, not a weakened active recipient session. Its encrypted locator contains the organization, envelope, recipient, original idempotency key, capability hash, and fixed `declinedAt + 30 days` expiry, but the public page returns only envelope/recipient IDs, both declined statuses, the timestamp, and locale. Every reload re-proves the command request fingerprint, the `recipient.declined` audit event and immediate predecessor, and the current revoked/scrubbed terminal projection in D1 or PostgreSQL. The original `/s/{capability}` URL can perform the same evidence-checked recovery after response loss; a successful new active link deletes any stale receipt cookie. Expired, malformed, unrelated, superseded, or projection-drifted locators share the inactive result and are deleted, while transient persistence failures preserve the cookie for retry. This path never invokes the document workspace service, Git archive, R2/S3, or recipient mutation endpoints, and the authoritative declined UI has no document or field branch in its server data or DOM.

### Operator voiding

Operator voiding is an organization-authorized `POST /api/v1/envelopes/{envelopeId}/void` command for `draft`, `ready`, `sent`, and `in_progress`. The request supplies both expected status and expected Git generation, so a stale confirmation or automation run cannot silently void a concurrently committed or sent envelope. The audit payload binds the previous status, generation, nullable repository head and sent pin, timestamp, and exact sorted IDs of capabilities revoked with reason `envelope_voided`; it excludes names, email addresses, capability hashes, ciphertext, key IDs, and delivery IDs. Publication uses the same terminal delivery boundary as decline: any `processing` lease fences the command; pending, blocked, and retryable-failed invitations become permanent terminal failures with ciphertext scrubbed; delivered and already-permanent evidence remains unchanged; every issued non-completed capability is revoked without changing recipient statuses. D1 performs this behind one rollback-on-failure command trigger, while PostgreSQL locks envelope, recipients, and delivery rows in stable order and verifies exact updated ID sets. The envelope transition, cleanup, revocation, receipt, and `envelope.voided` audit append are atomic. Exact-key replay rehashes receipt and audit evidence and rechecks the current terminal projection; fresh keys on terminal envelopes are rejected. If a D1 processing lease disappears between trigger rollback and failure classification, the conservative response is unavailable and a retry is safe. Undo, free-form reasons, object deletion, accepted-message cancellation, and role-specific organization RBAC are out of scope.

### Recipient approval

Recipient approval is a separate explicit `POST /api/v1/signing/approve` confirmation, available only to an active approver who has already viewed the documents. It uses the encrypted recipient cookie as sole authority and treats submitted envelope/recipient IDs only as equality constraints; same-origin, a required bounded idempotency key, `application/json`, and a 4 KiB body cap are all enforced before the cookie is read. One atomic publication marks the actor `completed`, revokes its capability, and appends a `recipient.approved` audit event. Signer and approver roles are the action-bearing workflow participants; viewer and prefill roles never block routing-group release or envelope completion. If signer or approver actions remain in a later routing order once the acting group clears, the same publication releases the next actionable order's reserved capabilities to a bounded expiry and reopens matching blocked delivery-outbox rows, including non-CC observers co-routed at that order, while leaving recipient statuses untouched. If no signer or approver action remains outstanding, the publication instead completes the envelope: `envelope` moves to `completed` and a second, deterministically chained `envelope.completed` audit event is appended in the same publication, its `previousHash` equal to the `recipient.approved` event's own hash — a two-event hash chain rather than a separate command. D1 uses one command insert plus a rollback-on-failure trigger that performs the actor update, the conditional group release or completion, and both audit inserts; PostgreSQL locks the envelope, every recipient, and the delivery outbox in stable order inside one transaction. The application layer retries only a bounded audit-head race with a fresh timestamp; every other terminal outcome (not found, context mismatch, role not actionable, idempotency conflict, integrity error) is returned unchanged on the first attempt. Exact evidence-checked replays succeed after response loss only under the original idempotency key, including when a later action has since advanced the envelope from `in_progress` to `completed`; a fresh key after revocation returns opaque not-found. The browser response clears the recipient session cookie only after a published or safely replayed approval; every other outcome, including a currently inactive or not-yet-eligible capability, leaves the cookie in place so an ambiguous or racy denial can never itself destroy a session a later request might still resolve.

Under this role contract, a released non-CC observer means `viewer`; prefill never enters the post-send graph. Final approval has an additional terminal boundary: before `envelope.completed`, any `processing` invitation lease fences the command with a retryable conflict. Otherwise pending, blocked, and retryable-failed invitations become permanent terminal failures with ciphertext scrubbed, and every outstanding issued non-completed capability is revoked without changing recipient status. Delivered and already-permanent evidence remains unchanged. D1 performs this in the command trigger and PostgreSQL under the existing ordered locks; completion replay also verifies that this terminal projection has not regained authority.

### Recipient signing

Recipient signing is a separate explicit `POST /api/v1/signing/sign` confirmation, available only to an active signer who has already viewed the documents. The encrypted recipient cookie remains the sole authority; submitted envelope/recipient IDs and `expectedFieldGeneration` are equality/CAS constraints against a freshly resolved capability and the current field-generation pointer, so a stale page cannot sign after labels or required flags change. Same-origin, a required bounded idempotency key, `application/json`, and a 2 MiB body cap sized for the maximum valid field set are enforced before the cookie is read. The body supplies exactly one value for every field this recipient owns, including the exact empty set when none are assigned: typed signature/initials, text, a real `YYYY-MM-DD` calendar date, or a boolean checkbox. Values are normalized (trim, type, calendar validity) before the request fingerprint is hashed, together with field generation, so equivalent submissions hash identically regardless of value order. Durable replay reconstructs that fingerprint from stored `field_value.value_json` rows and fails closed if the digest, audit chain, or one-shot field set cannot be proven. Raw values and labels are written only to SQL; `recipient.signed` carries value SHA-256 digests, and the public receipt never echoes values, labels, audit hashes, or capability material. One atomic publication completes the actor, revokes its capability, inserts immutable field values, pins the sent commit and field generation, and either releases the next signer/approver order with its co-routed viewers or performs the same lease-fenced terminal cleanup as approval before completing the envelope with a chained `envelope.completed` event. D1 inserts the command through a rollback-on-failed-predicate trigger, then inserts `field_value` rows as later statements in the same batch; PostgreSQL locks the envelope, recipients, delivery outbox, envelope fields, and existing field values in stable ID order inside one transaction. Only the original idempotency key can recover an evidence-checked terminal receipt after response loss; a fresh key after revocation returns opaque not-found. Ink, PDF, DOCX, webhooks, and rate limits are out of scope.

Agents and the future CLI use revocable instance-scoped API keys (`signkit_` prefix) owned by an authenticated local `instance_member`, with explicit scopes such as `envelopes:read`, `drafts:write`, and `envelopes:send`. They never use browser cookies or the OAuth client secret. Create, list, and revoke are owner-scoped and require that member to be currently `active` at the durable D1/PostgreSQL boundary; suspended members fail closed. Key ownership is not organization membership and grants no cross-organization access. Create, list, and revoke are exposed as owner-scoped d6e-auth-authenticated HTTP endpoints.

## API key Bearer authentication and organization grants

An agent authenticates with `Authorization: Bearer signkit_<43 base64url characters>` and must name the organization it intends to act within using a `SignKit-Organization-Id` request header. Both are mandatory and neither is ever inferred. A key holding exactly one live grant still has to name it; a key holding several reaches only the one it asked for; and the browser organization cookie, grant insertion order, and any notion of a "first" or "default" grant play no part in the decision. Silent inference is the specific failure mode this rule exists to prevent, because it would let a key act inside a tenant its caller never intended.

Key ownership remains strictly separate from organization access. A live `api_key_organization_grant` row is the only thing that lets a key reach an organization, and effective authority is the key's own canonical scopes intersected with that one requested live grant: a grant adds an organization and never adds a scope. Grants carry no expiry of their own, so the owning key's `expires_at` is the only lifetime, and a key may hold live grants for several organizations at once. Active uniqueness is `(api_key_id, organization_id)` among unrevoked rows only, enforced by a partial unique index, so history is append-only: revocation stamps `revoked_at`, never deletes or clears it, and re-granting the same organization after revocation mints a new row rather than resurrecting the old one. D1 makes that append-only discipline a property of the table with rollback triggers, matching `instance_member_command`; PostgreSQL keeps it in the adapter transaction as every other PostgreSQL migration in this repository does.

Resolution happens once per request in a SvelteKit server hook, against a narrow path allowlist that currently contains only `/api/v1/envelopes` and its descendants. Everything outside that allowlist — the recipient signing surface, public completion artifacts, the system drains, and every browser page — never resolves an API key at all, so a key presented there cannot authenticate regardless of what the endpoint handler does. Membership in the allowlist only means a key may be resolved on that path; it never means every endpoint beneath it accepts one, and the two layers stay independent so widening the allowlist can never by itself hand a key a mutation.

API key and instance management are a third case: there, a well-formed `signkit_` bearer is _rejected_ rather than ignored. Merely not resolving it would be insufficient, because a request carrying both a key and a browser cookie would then be authorized by the cookie — which is precisely the escalation path a key must never have, since these are the surfaces that mint keys, grant organizations, revoke grants, and administer instance members. Presenting a key on `/api/v1/api-keys/**` or `/api/v1/instance/**` therefore fails closed with a 403 and suppresses the cookie for that request, so the two authorities cannot compose where composing them would matter most. No durable read happens: the refusal follows from where the key was presented. Only a well-formed `signkit_` value triggers it — any other `Authorization` value on those paths is not an API key and keeps that endpoint's prior handling — and `POST /api/v1/instance/bootstrap` is deliberately exempt, because its `Authorization` header is not a credential-family selector but carries `SIGNKIT_BOOTSTRAP_SECRET`, whose constant-time check already precedes identity and already answers an opaque 404 for any wrong value.

Bearer mode is exclusive and is selected by a _non-empty_ `Authorization` value, not by its validity. An absent header and a present-but-empty one are deliberately equivalent -- `Headers.get` yields `null` versus `''`, and HTTP strips surrounding whitespace so a whitespace-only value is also empty -- because an all-empty `Authorization` carries no credential and therefore cannot compose with a cookie; suppressing the cookie for it would only turn a credential-free request into a 401 for no gain. Header duplication does not evade this either: repeated fields join with `", "`, so an empty value alongside a real token yields a non-empty combined value that the anchored parse refuses, with the cookie suppressed. Once one is presented on an allowlisted path, the cookie session is not resolved for that request at all: a malformed bearer, a foreign credential family, or an unauthorized key fails closed instead of silently inheriting whatever browser session accompanied it, and a valid session can never rescue a failing key. Only a strict full `signkit_` token authenticates; a recipient capability (`skr1_`), a completion access grant (`skca1_`), an instance invitation token (`ski1_`), a deployment worker secret, a lowercase `bearer` scheme, and any malformed value all resolve to the same opaque outcome, so presenting one reveals nothing about which credential families exist. Every other credential family keeps its existing handling untouched, including instance bootstrap's distinct deployment-secret-plus-cookie flow, whose constant-time secret check still precedes identity and still answers an opaque 404; bootstrap is therefore deliberately exempt from the rejection rule below, because a `signkit_`-shaped value in its `Authorization` header is simply a wrong deployment secret and already fails closed.

API key and instance management paths go further than merely not resolving a key: presenting a well-formed `signkit_` token there is an error in itself. Ignoring the header would not be enough, because a request carrying both a key and a browser cookie would then be authorized by the cookie — precisely the escalation an API key must never have, since these are the surfaces that mint keys, grant organizations, and administer instance members. Such a request is therefore classified as a rejected surface with no durable read at all, the cookie is suppressed along with it, and the endpoint answers 403. Each management handler independently refuses a presented key as well, so the guarantee holds locally even if the surface lists change.

Every request re-reads the token hash, the key's revocation and expiry, the owner's `instance_member` status, the stored canonical scopes, the requested live grant, and the granted organization's projection row. The whole decision is one statement, therefore one durable snapshot, so a revocation or suspension committing mid-resolution is either wholly visible or wholly absent and a principal can never be assembled from two points in time. Nothing is cached anywhere, which is what makes revoking either the key or the grant effective on the very next request. Keys are found by `token_hash` only — `key_prefix` is display material many keys share and is never a lookup term — and neither the presented token nor its hash is ever logged, returned, or persisted. `last_used_at` and the `rate_window_*` columns stay deliberately unwritten in this slice; populating them would turn every agent read into a write and is tracked separately, as are rate limits.

Outcomes are ordered so that each discloses only what its recipient already holds. A missing or malformed organization selector is a 400 decided before any durable read, so it says nothing about the token. An unknown token hash, a revoked key, an expired key, and a suspended or missing owner share one opaque 401 carrying a bare `WWW-Authenticate: Bearer` challenge with no `error` parameter and no credential detail, so the endpoint is not an existence or status oracle. A live key with an active owner but no live grant for the requested organization is a distinct 403: that reports only the caller's own authority over a credential they are already holding, and collapsing it would leave a correctly configured agent unable to tell a missing grant from a bad token. Insufficient scope is a separate 403 evaluated last, so scope never leaks which organizations a key can reach. Integrity drift — non-canonical stored scopes, more than one live grant for the requested pair, or a granted organization with no projection row — and an unresolvable store are both 503, never a downgrade to unauthenticated. All of these are RFC 9457 problem documents with stable `type` URNs.

This slice enables `envelopes:read` on the organization-authorized envelope reads: `GET /api/v1/envelopes`, `GET /api/v1/envelopes/{envelopeId}`, `GET /api/v1/envelopes/{envelopeId}/draft`, `GET /api/v1/envelopes/{envelopeId}/docx`, `GET /api/v1/envelopes/{envelopeId}/deliveries`, and `GET /api/v1/envelopes/{envelopeId}/completion-artifact`. `drafts:write` and `envelopes:send` are accepted on the authoring and send/void mutations listed by `GET /api/v1/system/capabilities`, including `POST /api/v1/envelopes/{envelopeId}/draft/docx`. `audit:read` can still be minted and stored, and is still canonicalized, but no endpoint accepts it. Agent mutations record `actor_type = 'agent'`. Completion-artifact publication still pins `envelope.created`, `envelope.ready`, `envelope.fields_placed`, `envelope.sent`, and `envelope.voided` to `actor_type = 'user'`, and `actor_type` is deliberately not part of those events' hash preimage, so an envelope whose create/ready/fields/sent/void events were written by an API key can fail closed at publication as `completion_artifact_evidence_invalid` until that allowlist is widened.

## Granting and revoking organization access

Granting requires two authorities in the same request, and that conjunction is the enforcement point for the ownership/access separation. The caller must hold live d6e authority over the target organization — an `owner` or `admin` role in the session-selected organization, taken from the verified d6e-auth membership — and must also be the key's own currently active `instance_member` owner, which the durable store re-proves. An instance administrator cannot grant on another member's key in this slice. The organization comes solely from the session; the request body is the exact empty object and cannot name an organization, so a caller can only ever grant an organization they are currently authorized for. The grant transaction upserts the organization projection from that same verified membership, so a d6e organization that has never created an envelope here still resolves the grant's foreign key. `POST /api/v1/api-keys/{apiKeyId}/organization-grants` is atomic over the projection, the grant row, and its Idempotency-Key receipt; an exact replay returns the original grant, a fresh key naming an already-granted organization returns that existing grant without writing a second receipt, and the two are reported distinctly so an unrelated request is never labelled an idempotent replay. A revoked or expired key is refused explicitly, while an unknown or cross-owner key id is opaque.

Revocation deliberately accepts _less_ authority than granting, because it is de-escalation, and it admits two independent paths. The key's own currently active instance-member owner may revoke with no d6e organization membership whatsoever, so losing organization access never strands an operator holding a key they cannot narrow. Separately, a current d6e `owner`/`admin` of the session-selected organization may revoke any grant _for that organization_ without owning the key and without holding any local instance membership at all; this is the immediate organization-side control over an agent, exercisable without waiting on the key's owner. Because that second actor need not be a local member, `api_key_organization_grant.revoked_by_user_id` and the revoke receipt's `actor_id` deliberately carry no foreign key to `instance_member`, and the applied path is recorded as `key_owner` or `organization_admin`. The organization scope is always resolved from the verified session and never from a request field, so an identity-only caller cannot name an arbitrary organization — they simply carry no organization scope and fall back to the owner path. Both paths are re-proven durably; when a caller holds both, `key_owner` is resolved first so the recorded authority is deterministic. The exact-key replay receipt is evaluated before authority, so an actor since suspended or since removed from the organization still sees their own earlier command replay identically. Listing a key's grant history (`GET /api/v1/api-keys/{apiKeyId}/organization-grants`) is owner-scoped only; there is deliberately no organization-side listing surface, because enumerating every key granted to an organization is a broader disclosure than revoking one grant an operator already knows about. Grant records store only UUIDv7 identifiers, key/organization/user references, the asserted grantor organization role as evidence, timestamps, and the revoking actor and path — never an email, a display name, a token, a token hash, or a key prefix.

One residual is deliberate and must not be mistaken for an oversight: losing d6e organization membership does not automatically revoke a durable grant. A grant is created under a live membership proof but outlives it, because d6e organization state is only knowable per request from d6e-auth while the grant is durable here. The immediate control is the organization-side revoke path above, which any current organization owner or admin can exercise without the key's owner. Automatic synchronization — a webhook or periodic revalidation from d6e-auth that retires grants whose grantor or organization has changed — is a follow-up, and until it exists an organization that removes an administrator should also revoke the grants that administrator created.

## Instance administration

### Instance bootstrap

`instance_member` is keyed by the external d6e-auth user subject. It stores role (`owner`, `admin`, or `member`, defaulting to `member`), status (`active` or `suspended`), and timestamps, and no PII. One-time instance bootstrap (`POST /api/v1/instance/bootstrap`) claims the initial active `owner` slot only when the instance is empty (both `instance_bootstrap` and `instance_member` have no rows), writing the singleton `instance_bootstrap` row and a durable `instance_bootstrap_command` receipt keyed by actor and `Idempotency-Key`. The endpoint requires a verified d6e-auth cookie session and `Authorization: Bearer SIGNKIT_BOOTSTRAP_SECRET` (checked constant-time before identity so invalid or unconfigured secrets return an opaque 404). Exact idempotency replays return safe 200 with current owner metadata; conflicting fingerprints return 409 conflict, and cross-subject or post-bootstrap requests return 409 already bootstrapped. `GET /api/v1/instance/members/me` requires identity only and returns `{ member, bootstrapped }`. Member administration is exposed in the `/settings` instance administration UI (see the member and invitation surfaces below). Explicit d6e organization grants for API keys are specified above under “API key Bearer authentication and organization grants”; they live in `api_key_organization_grant` plus its two command receipts, which are the one place an instance-scoped table deliberately names an organization, because bridging a local key to an external tenant is exactly their purpose. Because SignKit is unreleased, rewritten migrations require existing local databases to be reset rather than compatibility-migrated.

### Member administration

Instance member administration — `GET /api/v1/instance/members`, `POST /api/v1/instance/members/{userId}/role`, and `POST /api/v1/instance/members/{userId}/status` — governs every already-enrolled `instance_member` row and is instance-scoped exactly like bootstrap and invitations above: ownership here is never a d6e organization role, only the local `owner`/`admin`/`member` triple. List is cursor-paginated with the same ceilings as invitations (default 25, maximum 100 per page) and requires the caller to be a currently active `owner` or `admin`, returning 403 `forbidden`/`member_suspended` otherwise. `setInstanceMemberRole` and `setInstanceMemberStatus` each take the target's user ID and a new role or status, are fingerprinted over the canonical `{ operation, targetUserId, role|status }` triple (zero-PII, no email or name), and are single atomic units writing the state change and its Idempotency-Key receipt together, matching bootstrap and the invitation store. An `owner` may administer any member; an `admin` is scoped to targets whose _current_ role is `member` and can never grant `admin` or `owner` — `role_not_permitted` is evaluated before the target-role `forbidden` check, so an admin requesting a role above `member` is rejected uniformly regardless of who the target is, including the admin itself. Role changes permit self-targeting, subject to the same owner floor as every other change: an update that would leave the instance with no active `owner` returns 409 `last_active_owner` instead of applying. Status changes never permit self-targeting at all, regardless of role, returning 409 `cannot_target_self` before the store is ever consulted. Demoting a member below the role it invited under, or suspending it outright, atomically cascades: the member's own still-pending invitations that its new role or status can no longer justify are revoked in the same transaction, and `revokedInvitationCount` in the outcome reports how many. PostgreSQL serializes every role/status change behind one shared `pg_advisory_xact_lock('instance_member_admin')`, acquired before the actor and target rows are locked `FOR UPDATE` in stable `user_id` order — the same lock-ordering discipline that lets invitation create/accept/revoke and member administration coexist without deadlocking, since neither path ever acquires a member-row lock after an invitation-row lock. D1 achieves the equivalent serialization through its existing rollback-on-failed-predicate command trigger, checking the exact-replay receipt first (so an actor since demoted or suspended does not change how their own earlier command replays) and rejecting a command whose `updatedAt` regresses behind the target's stored `updatedAt` as an `integrity_error`. An exact `Idempotency-Key` replay returns 200 with `idempotency-replayed: true` and the original call's receipt-recorded `member`, `appliedAt`, and `revokedInvitationCount`, never state recomputed from what a later command produced; a reused key against a different request returns 409 conflict, and an unknown `targetUserId` returns 404 `member_not_found`. This surface backs the members tab of the `/settings` instance administration UI, where an owner or admin lists members and applies role and status changes within exactly the authorization rules above.

### Instance invitations

`instance_invitation` extends the same zero-PII discipline: no email, name, or plaintext token is ever persisted, only a UUIDv7 `id`, `role`, `status` (`pending`, `accepted`, or `revoked`), the inviter/accepter/revoker subjects, timestamps, a SHA-256 `tokenHash` of the bearer `ski1_` credential, and an `emailBinding` — a hash of the token concatenated with the normalized invited address, so the binding can only be reproduced by a party who already holds the raw token and is asserting a specific address; the database never stores anything that lets a holder enumerate invited addresses. `POST /api/v1/instance/invitations` requires the actor to be a currently active `owner` or `admin`, accepts only `email` and `role`, and always assigns the fixed 7-day expiry — the public HTTP surface never accepts a caller-supplied expiry. The command's idempotency fingerprint is the canonical `{ role }` only, deliberately excluding the invited email to keep the receipt zero-PII; the practical consequence is that replaying the same `Idempotency-Key` for a different invitee is indistinguishable from a safe replay and silently returns the original invitation rather than inviting the new address, so callers must mint one fresh `Idempotency-Key` per invited address rather than reusing a client-side default. `GET /api/v1/instance/invitations` is cursor-paginated and requires the same active `owner`/`admin` authorization as create. `POST /api/v1/instance/invitations/accept` resolves the invitation by `tokenHash` and recomputes `emailBinding` from the bearer token and the caller's own already-authenticated d6e-auth identity email claim — never a request-body field — so acceptance is proven by holding the token for that asserted address; d6e-auth exposes no distinct `email_verified` claim, so this is an authenticated assertion, not a provider-verified guarantee. An unknown, expired, non-`pending`, or wrong-email token and an already-suspended accepting member resolve to the identical opaque outcome, so a caller cannot distinguish "bad token" from "suspended target account." A currently _active_ accepting member is a separate, non-opaque case: the store returns `already_member` — proven ahead of the receipt-replay and invitation checks by the actor's own current status, before the invitation is ever locked or mutated — and the endpoint returns 409 `instance-member-already-exists` carrying only that actor's own current member metadata, never the invitation or token; the invitation itself is left `pending` and no receipt is written, since re-accepting cannot change an existing member's role and the caller already knows their own membership. `POST /api/v1/instance/invitations/{invitationId}/revoke` is scoped to a currently active `owner`/`admin` actor; a suspended actor returns 403, and an admin forbidden from revoking a non-member-role invitation also returns 403 — not opaque, since list already exposes every invitation's role to any owner/admin — while an unknown or already-resolved invitation ID returns 404. All three mutations are single atomic units writing the state change and its Idempotency-Key receipt together, matching bootstrap and the API key store. Existing members' roles and statuses are never changed by accepting an invitation; that is the explicit instance member administration API described above, which is also the mechanism that cascades a revoke of an inviter's own pending invitations when its role or status changes. Invitation create, list, revoke, and token accept are exposed in the `/settings` instance administration UI, which reveals the one-time `ski1_` token to the inviter exactly once; invitation email delivery itself remains deferred, so that token must be handed to the invitee out of band.
