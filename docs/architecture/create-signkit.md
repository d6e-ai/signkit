# create-signkit (Cloudflare deployment CLI)

Status: implemented (Cloudflare slice)

Last updated: 2026-11-20

`create-signkit` is the **deployment** CLI. It publishes a verified GitHub Release of SignKit onto Cloudflare Workers, D1, and R2. The manifest SHA-256 detects transport corruption; mandatory GitHub/Sigstore provenance independently authenticates the downloaded bundle, source repository, tag, commit, and the release workflow or pinned maintainer that attested it ([release provenance](#release-provenance)). It is not the Rust SignKit API CLI (`signkit` under `cli/`), which talks to an already-running instance over `/api/v1`.

The two CLIs do not share configuration, credentials, or state. Mixing them is a usage error, not a fallback.

## Syntax

Every command requires an explicit boolean provider flag **before** the command token:

```text
create-signkit --cloudflare <plan|deploy|adopt|upgrade> --account-id <id> [options]
```

Cloudflare is not an implicit default. Invoking a command without `--cloudflare` fails with exit 2. `--node` and `--vercel` are reserved, mutually exclusive with `--cloudflare`, and unimplemented in this slice.

## Commands and the reconciler

All four commands share one idempotent reconciler. The reconciler never deletes Cloudflare resources.

| Command   | Mutations        | Behavior                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| --------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `plan`    | none             | Resolve a GitHub Release, download the exact bundle, verify its mandatory online provenance, inspect resources, and print the plan. Planned mutation steps keep `mutating: true` but are not executed. Drift is reported in JSON and in human `Drift:` output, not thrown.                                                                                                                                                                                                                                                                              |
| `deploy`  | yes              | Create missing D1/R2 only when there is no local state and the remote identity is absent, then follow the deployment sequence. A Worker that already has published versions **or stored secrets** requires `adopt` first; there is no secret-only stub flow. On a genuinely pristine initial deploy (no local state, no remote Worker versions/secrets), bound recovery material is created/reused from stdin OAuth JSON, or from [console enrollment](#console-enrollment), before any Cloudflare mutation and staged for upload via `--secrets-file`. |
| `adopt`   | local state only | Validate intended existing Worker/D1/R2 and record them in local state. Does not resolve or claim a GitHub release.                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `upgrade` | yes              | Require recorded local state and existing resources. A no-state upgrade refuses to take over a remote Worker and requires `adopt` first. Identity drift cannot be bypassed with resource flags. Apply pending migrations, re-list and refuse remaining pending, then upload and deploy the Worker version before reconciling routes and Cron Triggers from the extracted release config.                                                                                                                                                                |

Mutating commands require `--yes`.

## Deployment sequence

1. Load XDG state and refuse `state.provider !== cloudflare` before inheriting anything. `upgrade` without local state refuses immediately (adopt first). Resolve the **effective config**. `--account-id` is always required and never inherited. Omitted `--worker-name`/`--d1`/`--r2`/`--domain`/`--public-origin` and safe mail/origin flags inherit from Cloudflare state **before** any Cloudflare inspection. Parser defaults are not treated as a requested identity when state exists.
2. `cf accounts list`: refuse if `--account-id` is not accessible to the session. Errors do not print account names or other account ids.
3. Inspect Worker/D1/R2 using the effective identity (read-only for `plan`). `adopt` stops here: it does not resolve or download a GitHub release.
4. `plan`/`deploy`/`upgrade` resolve a GitHub Release, download its bundle once, validate its size and SHA-256, and require online GitHub/Sigstore provenance verification. The verified bytes are retained in memory and are the only bytes later extracted. Missing, unavailable, malformed, oversized, invalid, or conflicting provenance fails before recovery-file creation, D1/R2 creation, backup, migration, or Worker upload. `plan` performs the same verification but remains mutation-free.
5. Resource validation. Missing D1/R2 that cannot be created (a D1 UUID that does not exist, or a missing resource on a run with local state) is refused before any recovery or enrollment step. On a pristine initial deploy, the deterministic recovery path is checked first. A valid existing file is reused without reading stdin; otherwise the OAuth pair comes from [console enrollment](#console-enrollment) when `D6E_ENROLLMENT_TOKEN` is set, or OAuth secrets are read once from stdin (bounded 16 KiB exact-key JSON), an adjacent non-secret `recovery-binding.json` binds the selected account and Worker, and the recovery file (`<state-dir>/recovery.json`: parent `0700`, files `0600` from creation, exclusive no-overwrite, symlinks/non-regular files refused via lstat, POSIX owner checked, fsynced, retained on success and failure) is created **before** creating D1 or R2. Windows is refused because these owner/mode guarantees cannot be enforced; WSL is supported. Retries must match the binding; an unbound or differently bound recovery file is refused. Manifest secret taxonomy is validated for every deploy and upgrade, and unknown types fail closed here with restore guidance. Only `path` and SHA-256 `fingerprint` are returned/logged. Otherwise, required Worker secrets are preflighted by name **before** creating D1 or R2. If any are missing, the valid bound recovery pair is required. The CLI re-reads and verifies the retained fingerprint, writes only the missing names into a private `0600` temporary upload file, preventing present remote secrets from being reset, and passes that path to the subsequent Worker upload with `--secrets-file`; existing deployments never generate or overwrite retained recovery material. Create missing D1/R2 on `deploy` only when local state is absent. If state names a resource that is missing remotely, that is drift (fail closed); do not recreate it.
6. D1 backup/export (`wrangler d1 export --remote`) to `$XDG_STATE_HOME/create-signkit/backups/d1-<name>-<timestamp>.sql`. The timestamp includes milliseconds; if that name already exists, a numeric suffix is added. The backups directory is created with mode `0700` at mkdir time, then chmod `0700`, and the file is chmod `0600` after export (POSIX fail-closed; Windows is best-effort because chmod maps to ACLs). The path is returned and stored as `lastD1BackupPath`. It is never placed under the temp bundle directory and is never deleted by the CLI.
7. Verify the release manifest's D1 schema epoch before applying migrations. A populated D1 may only be upgraded by a release with the epoch recorded in local state. A missing or different epoch is accepted only when the selected D1 ledger has no applied migrations, which is the fresh-database reset path. Otherwise the CLI refuses the in-place upgrade and directs the operator to recreate and adopt D1. Pending migrations run only from the **extracted release** (`cf d1 migrations list|apply <database-id> --dir <extracted migrations directory>`). cf uses the remote API by default here; local development never reuses this command implicitly. The listing is parsed strictly and an explicit `cf d1 query` reads the applied ledger, so malformed output cannot masquerade as a fresh database or an empty pending set. After a successful apply, migrations are listed again and remaining pending names fail the command. `newlyApplied` is the pre-apply pending list, unioned with existing `state.appliedMigrations`, and the same value is written on success and on smoke failure.
8. Worker upload/deploy with `--keep-vars`, `--strict`, and `--no-bundle`. Routing comes only from the validated generated config, never a `--domain` argument to Wrangler. A Worker without versions requires a complete first `wrangler deploy`; existing Workers use `wrangler versions upload`, publish the exact uploaded version at 100% with `cf workers deployments create`, and then reconcile routes and Cron Triggers with `wrangler triggers deploy`. Dashboard vars and secrets are preserved; secrets are never deleted by deploy. Upload is a hard failure if Wrangler exits 0 without a labelled Worker/Version ID, aborts, or reports a remote override. A D1 UUID in that output is never treated as the Worker version. The new version id must differ from the previous one. Worker versions are sorted by `createdOn` descending (missing timestamps last, stable original order among equals) before identifying the previous version. Publication must return the requested version at exactly 100%; no deployment-check bypass is used. A failed first deploy that nevertheless created a version, or a failed trigger reconciliation, records `triggerReconciliationRequired` and stops before smoke; it does not attempt an automatic Worker-only rollback.
9. HTTPS smoke check of `GET /api/v1/system/capabilities` on `--public-origin`, implied `https://<domain>`, or the production `{worker-name}.*.workers.dev` origin, with escalating bounded retries (default 1s then 2s) and a per-request AbortSignal timeout. Version-preview URLs are never used as production verification. If no production origin is known, smoke is reported as skipped and the command fails. A custom domain explicitly disables `workers.dev`, which is therefore never used as fallback. Hosts are only the validated origins already selected for this run. Failure retains the deployed Worker, routes, and Cron Triggers for explicit operator reconciliation.

Migrations run **before** the new Worker is uploaded so the still-serving previous Worker must keep working on the new schema.

## Migration policy

Released D1 migrations are **additive within a named schema epoch**:

- Forward: a new Worker may assume the schema produced by applying its pending migrations.
- Backward: the previous released Worker must keep running after those migrations are applied, because Worker rollback cannot roll back D1.
- Epoch change: a populated D1 is never upgraded in place. The database must be recreated, adopted, and initialized from the new release.

A failed or skipped HTTPS smoke check leaves the newly deployed Worker, routes, and Cron Triggers active and records that coherent state for operator reconciliation. The CLI never performs a Worker-only rollback after trigger configuration has changed and never claims that D1 was rolled back. Operators who need SQL restore use D1 Time Travel ([operations/d1-time-travel-restore.md](../operations/d1-time-travel-restore.md)).

## Version resolution

Versions come from GitHub Releases of `d6e-ai/signkit`, never from arbitrary git refs. Tags with semver build metadata (`+build`) are rejected. Manifest `channel` is classified from the tag's semver prerelease component (`v1.2.3-beta.1` is beta; `v1.2.3` is stable), not from a substring match. The tag workflow creates the GitHub Release as a draft with the matching `prerelease` flag. A rerun refuses a public release or mismatched draft metadata instead of editing it, and it reuses an existing expected asset only after downloading and comparing the complete bytes; mismatched or unexpected assets fail closed and are never replaced. npm publish uses dist-tag `beta` for prereleases and `latest` for stable, also from that classification. `SIGNKIT_RELEASE_TAG` overrides `GITHUB_REF_NAME` when both are set so CI branch names cannot become the synthetic bundle tag.

- `--version latest --channel stable` uses `/releases/latest` (non-draft, non-prerelease, stable semver tag). A beta/prerelease is refused.
- `--version latest --channel beta` selects the highest valid semver prerelease tag among non-draft releases, independent of GitHub API order. Drafts, stable tags, and invalid/build-metadata tags are ignored. If none exists, the CLI fails rather than selecting a stable release.
- `--version v1.2.3` is an exact tag fetched from `/releases/tags/v1.2.3`. `--channel` is still enforced against the tag, GitHub prerelease metadata, and the manifest channel, so stable never resolves a beta.
- Release tags are limited to 35 ASCII bytes. This keeps every pinned Fulcio certificate claim within DER UTF8String short-form encoding; longer tags fail deterministically during release selection, before bundle or attestation download.

Each release must publish `signkit-cloudflare-manifest.json` and a `signkit-cloudflare-<tag>.tar.gz` bundle. The CLI validates schema, repository, tag, commit, size, and SHA-256, and will only download from bounded allowlisted GitHub release/API hosts. The tag workflow asks GitHub to create signed SLSA provenance after the complete draft asset set has been uploaded or byte-verified. After npm publication succeeds, the final job re-downloads the exact remote asset set and verifies every byte against SHA-256 values passed directly from the build job before making the draft public. The maintainer release script keeps the same order and checks without GitHub Actions ([release checklist](../release-checklist.md#5-maintainer-signed-release-without-github-actions)). Repository immutable releases are also required before a tag is pushed.

## Release provenance

For both stable and beta channels, `plan`, `deploy`, and `upgrade` query the official `d6e-ai/signkit` repository attestation endpoint by the SHA-256 of the bytes just downloaded. Each returned Snappy bundle is bounded before and during decompression and cryptographically verified with the online Sigstore public-good trust root, requiring at least one certificate transparency SCT and one transparency-log entry. Every returned attestation must verify as one of two kinds below, and all attestations for the digest must be of the same kind; conflicting, mixed, or partially invalid results fail closed. Offline verification and stale trust-root fallback are intentionally unsupported. Results expose a non-secret `provenance` object in JSON, whose `kind` is `workflow` or `maintainer`, and a concise verified line in human output; signed bundle URLs and certificate material are never printed. `adopt` does not select a release and therefore has no provenance result. The npx package does not require this repository or pnpm; it carries cf, the scoped Wrangler compatibility client, Sigstore verification, bounded Snappy decoding, and a tar extractor.

### Workflow attestations

The normal immutable-release path is the exact `release-cloudflare-bundle.yml` workflow dispatched from `refs/heads/main`; a tag-push run of the same workflow at `refs/tags/<tag>` is also allowed. Certificate claims and the signed SLSA statement must agree on the immutable repository/owner ids, public GitHub-hosted runner, allowed event/ref pair, source commit, workflow path, builder identity, current owner/repository-id-qualified runner identity, bundle basename, and digest. The GitHub Release tag and manifest must resolve to the same signed commit, so a dispatch from another branch or commit still fails closed. Multiple byte-equivalent workflow rerun attestations are accepted.

### Maintainer signatures

When GitHub Actions cannot run, a maintainer builds the release on their own Linux machine and signs it with Sigstore keyless signing after signing in with their GitHub account (`scripts/release-local.mjs`). The bundle is stored through the same repository attestations API, so the lookup by digest is unchanged. Such an attestation is accepted only when all of these hold:

- The Fulcio certificate's OIDC issuer is exactly `https://github.com/login/oauth`, the issuer Sigstore public-good records for a GitHub account sign-in, and its email subject alternative name exactly equals an entry pinned in `packages/create-signkit/src/release/maintainer-signers.ts`. The match is exact and case-sensitive.
- The signed in-toto Statement v1 has predicate type SLSA provenance v1 and build type `https://github.com/d6e-ai/signkit/release/maintainer/v1`, and its `externalParameters` are exactly `repository` (`https://github.com/d6e-ai/signkit`), `ref` (`refs/tags/<tag>` of the selected release), and `commit` (the release's resolved commit, which the manifest must also name).
- Exactly one subject names the Cloudflare bundle asset with the downloaded digest. The release script lists every release asset as a subject.

Any other build type takes the workflow rules and is rejected there. Several maintainer attestations for the same digest, such as a re-signature, are accepted when each verifies.

The pinned list is code, not configuration: each create-signkit version accepts exactly the identities in the commit it was built from, and no flag, environment variable, or state file extends it. The repository ships the list empty, which rejects every maintainer signature. The release owner adds or removes identities in a reviewed commit, and that commit must be on `main` before the release it signs is built. Removing an identity protects only create-signkit versions published afterwards. Versions before maintainer support accept only workflow attestations and refuse maintainer-signed releases.

Trust assumptions. A maintainer signature shows that someone who could sign in to a pinned GitHub account approved these exact bytes as this tag and commit. It does not show that they were built from that commit on an uncompromised machine, and nobody rebuilds them independently: the maintainer's workstation and the GitHub account's sign-in (password, two-factor authentication, sessions) replace GitHub-hosted runners and the reviewed workflow as the root of trust. Sigstore's public-good OIDC provider and Fulcio attest that GitHub reported the email as verified for that account. The certificate, including the email, is public in the Sigstore transparency log and in the stored attestation. create-signkit enforces the pinned identity but neither prints nor returns the email: the list shipped in the package is the trust anchor, and deploy logs should not carry a person's address.

## State and secrets

Non-secret deployment metadata is stored in `$XDG_STATE_HOME/create-signkit/state.json` (or `--state`). Safe vars stored there include worker/D1/R2 identity, optional domain, `publicOrigin`, `d6eAuthBaseUrl`, `emailFrom`, `emailFromName`, the mail-provider selection and non-secret SMTP connection settings, `bootstrapOwnerEmail`, `consoleOrigins`, `lastD1BackupPath`, and the D1 schema epoch. The file must never contain tokens or passwords.

Secrets are never accepted on argv and are never printed. Both CLIs run through their packaged Node entrypoints with a **minimal env allowlist** (PATH, HOME/platform, locale/TLS/proxy, XDG, CLI/Cloudflare auth) plus `CLOUDFLARE_ACCOUNT_ID` and `CI=1`. Parent env is not forwarded. The child-argv guard allows `--config`/`--secrets-file` paths but still rejects secret-bearing flags and secret-like values. On non-pristine commands, Worker secrets are preflighted by name via `cf workers secrets list --worker <name>`; missing names require the retained flat recovery JSON and matching target-binding sidecar before any D1 export, migration, or Worker upload. Malformed, oversized, or duplicate secret-name metadata fails closed instead of being treated as a pristine Worker. Validated values are copied into a private `0600` temporary file and passed as `wrangler deploy|versions upload --secrets-file <temporary.json>` (with `--keep-vars --strict --no-bundle`); existing deployments stage only missing names, and no secret-only Worker stub is created.

The **initial managed deploy** is a pristine `deploy`: no local Cloudflare state and no remote Worker versions/secrets. That deploy requires `--email-from` and `--public-origin` or `--domain`, reads its required secrets once from stdin, and writes every manifest `requiredVars` into the generated config. `SIGNKIT_MAIL_PROVIDER` defaults to `cloudflare`; an explicit `smtp` selection adds bounded SMTP vars, rejects port 25, omits the `EMAIL` binding, and accepts `SIGNKIT_SMTP_PASSWORD` only through secret stdin when a username is configured. The remaining generated vars include `SIGNKIT_PUBLIC_ORIGIN`, `D6E_AUTH_BASE_URL` (default `https://www.d6e.ai`), `SIGNKIT_EMAIL_FROM`, and `SIGNKIT_EMAIL_FROM_NAME` (default `SignKit`). The generated `wrangler.jsonc` also carries top-level `secrets.required`, explicit `workers_dev`, and the selected custom-domain route when present, so a later upgrade reconstructs the same routing intent from stored state. `plan` never reads stdin and never creates deployment/state/recovery files; online verification may create or refresh Sigstore's standard per-user TUF trust-metadata cache. Later deploys/upgrades may inherit non-secret values from state; `--keep-vars` leaves remote vars that are omitted from the generated config. Secrets are preflighted before any D1/R2 create. Secrets are never stored in state or logs — results carry only `recoveryPath`/`recoveryFingerprint`.

An existing deployment may change providers through explicit `upgrade` flags. When authenticated SMTP is selected after the pristine deploy, `SIGNKIT_SMTP_PASSWORD` must already exist in Worker secret storage: the retained recovery file is immutable and is never rewritten with a later operator credential. Missing provider-required secrets fail preflight before D1 backup, migration, or Worker upload.

Release tarballs accept only regular files and directories. Extraction fails closed if uncompressed regular-file bytes or member count exceed the cap, and rejects link, device, FIFO, and tar extension/PAX members. Bundle paths stay short relative POSIX names so PAX long-link headers are not required.

This CLI does **not** add a bootstrap secret. It requires a deployer-selected `--bootstrap-owner-email` and writes it as the non-secret `SIGNKIT_BOOTSTRAP_OWNER_EMAIL` Worker variable, so only that verified d6e-auth email can make the first-owner claim. Operators must still call `POST /api/v1/instance/bootstrap` before advertising the URL. See [authorization-and-instance-administration.md](authorization-and-instance-administration.md#instance-bootstrap).

## Console enrollment

A pristine initial deploy may obtain its OAuth client from D6E Auth instead of stdin. The operator receives a single-use console enrollment token from the SignKit console and supplies it only through the `D6E_ENROLLMENT_TOKEN` environment variable; argv never accepts it, and it is never printed, stored, or forwarded to cf/Wrangler (their child environment is an allowlist). The value must be `d6ee_` followed by 43 base64url characters; anything else is a usage error that does not echo the value. `plan` never calls D6E Auth: with a token on a pristine target it lists a mutating `console-enrollment` step.

Enrollment runs only when all of these hold: `deploy`, no local state, no remote Worker versions or secrets, no retained recovery file, and no retained enrollment record. Every check that does not need D6E Auth runs first: account access, remote inspection, release resolution and provenance, secret taxonomy, initial vars (`--email-from`, `--public-origin`/`--domain`, an explicit `--bootstrap-owner-email` if given), resource creatability, the recovery directory and target binding, and, for authenticated SMTP, the secret stdin JSON, which then carries exactly `SIGNKIT_SMTP_PASSWORD`. Only then does the CLI send one request:

```text
POST {D6E_AUTH_BASE_URL}/api/v1/console/enrollments
Authorization: Bearer <D6E_ENROLLMENT_TOKEN>
Content-Type: application/json

{"kind":"signkit","publicOrigin":"<effective public origin>","name":"<--server-name, or the public origin's hostname>"}
```

The request goes only to the effective `--d6e-auth-base-url` host over HTTPS, with a bounded response and timeout, and redirects are never followed, so the bearer cannot be replayed elsewhere. A `200`/`201` is used only when it is completely valid: `server.id` present, `server.kind` is `signkit`, `server.origin` equals the public origin, `clientId`/`clientSecret` satisfy the stdin OAuth rules, `bootstrapOwnerEmail` is an email address, `consoleOrigins` is a list of at most 16 `https` origins (`http` only for loopback) without path, query, or fragment, and `d6eAuthBaseUrl` equals the origin the CLI called. The CLI never adopts a different authority from a response body; a mismatch is a configuration error. An invalid success saves nothing and names the server id, because the registration may exist in D6E Auth without its secret.

After a valid response, `clientId`/`clientSecret` become `D6E_AUTH_CLIENT_ID`/`D6E_AUTH_CLIENT_SECRET` in the retained recovery file exactly as stdin OAuth JSON would. The non-secret remainder is written beside it as `<state-dir>/enrollment.json` (same directory and `0700`/`0600`, exclusive, fsynced, retained): `serverId`, `publicOrigin`, `d6eAuthBaseUrl`, the canonical lowercase `bootstrapOwnerEmail`, and `consoleOrigins`. The bootstrap owner defaults to `bootstrapOwnerEmail` when neither the flag nor state names one, and `SIGNKIT_CONSOLE_ORIGINS` defaults to `consoleOrigins` joined with commas. Results gain a non-secret `enrollment` object (`status: enrolled|reused`, `serverId`, `recordPath`) and mutation `enrollment`.

Failure handling:

| Outcome                                          | Exit / code                     | State left behind                                                                                                  |
| ------------------------------------------------ | ------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `401`                                            | 6 `enrollment_invalid_token`    | Binding only. The token is invalid, expired, or used; issue a new one.                                             |
| `409`                                            | 4 `enrollment_conflict`         | Binding only. An active SignKit server already uses the origin, or the issuer's email is unverified.               |
| `400`                                            | 6 `enrollment_invalid_request`  | Binding only.                                                                                                      |
| `429`, `5xx`, network error, or timeout          | 5 `enrollment_unavailable`      | Binding only. D6E Auth may or may not have processed the request; rerun with the same token.                       |
| `3xx`                                            | 1 `enrollment_redirect`         | Binding only; the redirect is not followed.                                                                        |
| Invalid `200`/`201`                              | 1 `enrollment_invalid_response` | Binding only; the response's secret is discarded.                                                                  |
| Recovery file cannot be written after a `201`    | 1                               | Binding only; fix the state directory and rerun with the same token to receive the server again with a new secret. |
| Record cannot be written after the recovery file | 6                               | Recovery file kept; rerun without the token and pass `--bootstrap-owner-email` and `--console-origins` explicitly. |

In every row Cloudflare is unchanged. A retry after any later failure (for example D1 creation or the first Worker upload) finds the recovery file and the enrollment record, never calls D6E Auth again, and reuses the same pair and defaults whether or not the token is still exported. The retry must keep the same public origin and D6E Auth origin as the record, because the OAuth client accepts only `<publicOrigin>/auth/callback`. A record without its recovery file, or a token alongside a recovery file without a record, is refused without using the token. A token set for a non-pristine deploy or an upgrade is refused unless an enrollment record shows that this deployment was already enrolled, in which case it is unused.

If D6E Auth processed the request but the response or the recovery file was lost, rerun the same command with the same token before it expires (30 minutes after issue): D6E Auth answers a repeated enrollment of the same origin with the same server and a new client secret, and the earlier secret stops working. After the token expires, a new token for the same origin receives `conflict` while the orphaned registration is active; an organization owner or admin disables it, or rotates its secret, under the organization's Auth Clients in the D6E account, then issues a new token.

`--console-origins <list>` sets `SIGNKIT_CONSOLE_ORIGINS` explicitly on any deploy or upgrade, with the same origin rules; an empty value writes an empty var, turning console CORS off. Like other non-secret vars it is recorded in state and inherited; when neither the flag, state, nor an enrollment names it, the generated config omits the var and `--keep-vars` leaves any remote value in place. The Worker's handling of the var is listed with the other runtime settings in [deployment](../deployment.md#configuration).

The enrollment response may also name `consoleUrl` (for SignKit, `https://www.d6e.ai/signkit/console`), which must be inside `consoleOrigins`; it becomes `SIGNKIT_CONSOLE_URL`, the place invitation emails offer for joining without the link, and is kept in the enrollment record and state. `--console-url <url>` sets or (with `""`) clears it explicitly on any deploy or upgrade.

## Drift

If local state, an explicit target, and remote identity disagree, mutating `deploy`/`upgrade` refuse. Supplying `--worker-name`/`--d1`/`--r2` that differ from state is still drift. `adopt` is the only command that records the intended existing resources into local state. `plan` reports `drift[]` without mutating, and human non-JSON plan output prints a `Drift:` list.

## Cloudflare command boundary

The reconciler consumes a tool-neutral `CloudflareClient` port. Its cf adapter invokes the packaged `cf/bin/cf` through Node for account access, D1 create/list/remote migrations and ledger reads, R2 inspection/creation, Worker secret-name inspection, and exact-version traffic publication. It does not depend on a global cf binary. Remote migration commands pin the selected D1 id and extracted release directory; output parsing is strict rather than guessing human tables or treating malformed rows as no migrations. Native traffic publication supplies only the selected Worker name and one version at 100%, without auto-provisioning or deployment-check bypass. The CLI must exit successfully and return an explicit deployment id and matching strategy/version/percentage before publication is accepted.

A Wrangler v4 compatibility client handles D1 export, legacy Worker version inspection, first upload, version upload, and route/Cron Trigger reconciliation. This is a deliberate migration boundary, not a claim that cf lacks every equivalent API. In the pinned beta, `cf workers versions list --worker-id` addresses `/workers/workers/{worker_id}/versions`, while the existing client addresses `/workers/scripts/{script_name}/versions`. Version inspection remains on Wrangler until equivalent Worker identity, timestamps, and missing-Worker behavior are proven. The current v1 archive does not carry cf Build Output, and native cf upload has not been proven to preserve its no-rebundle, strict override, retained-var, and secret-file guarantees. The compatibility client keeps `--config --name --strict --keep-vars --no-bundle` and the labelled Worker/Version id checks. Initial deploy and version upload receive routing from the validated generated config, never `--domain`. Existing Workers publish a version through cf and then reconcile routes and Cron Triggers; partial failures retain explicit reconciliation state instead of attempting a Worker-only rollback. The next phase must materialize validated prebuilt output from authenticated release bytes, test equivalent preservation/publication and partial-failure recovery behavior, and prove a canary install/upgrade/reconciliation before removing this compatibility path.

Both tools use minimal environments and fresh empty temporary working directories for account/resource discovery, so caller `.env` and project configuration cannot be implicitly selected. Worker uploads explicitly use the extracted bundle and its generated `--config`. A shared API token authenticates both; their stored OAuth sessions are separate. Missing-Worker classification and stdout/stderr/JSON behavior retain the existing strict contract. `upgrade` still refuses an explicit domain/origin that differs from stored state.
