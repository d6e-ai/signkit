# Completion artifacts and capability reissue

Status: implemented — manifest publication, delivery, visual completion PDF rendering, and capability reissue; cryptographic PDF sealing is backlog

## Completion artifact publication (Slice A)

Completion evidence is published by a durable reconciliation job, never by extending the hot `recipient.signed`/`recipient.approved` completion transactions. A periodic worker discovers envelopes with `status = 'completed'` and no published artifact — including envelopes that completed before this feature shipped — and leases exactly one dedicated `completion_artifact_job` row per envelope, mirroring the invitation outbox's bounded-claim, five-minute-reclaim, capped-backoff, and stable-safe-error-code pattern rather than reusing the invitation `delivery_outbox` table.

Once completed, an envelope's `sent_commit_sha`, `repository_head`, `field_generation`, recipients, fields, and audit chain are all immutable, so the worker rebuilds the canonical `signkit-completion-manifest-v1` manifest deterministically from the pinned Git revision (read the same way as `readImmutableDraftRevision`, whose `DraftIntegrityError` — a missing object, a SHA-256 mismatch, an organization-scope mismatch, a size violation, or a Git verification failure — is classified as a non-retryable integrity failure here exactly like the worker's own evidence checks, since R2/S3 are strongly consistent for these immutable pointers; a raw provider read error that is not itself a `DraftIntegrityError` is not assumed to be tampering and remains retryable). The document-set manifest is parsed from those already-verified archive bytes — never from a second, unverified object-store read. SQL evidence supplies the envelope ID and title, `sent_commit_sha`, the draft archive SHA-256, the field generation, `completedAt`, sorted documents (Markdown path/content digest, plus `id`/`kind`/`position`/`title` and `documentSetHash` for envelopes sent after per-document publication; PDF leaves carry the PDF digest/size/pages and are referenced, never inlined, in the visual completion PDF), sorted recipient ID/role/routing-order/status plus each actionable recipient's decision audit event ID and timestamp, sorted field ID/type/value-SHA-256 triples, and an audit proof. When a `documentSetHash` is present, publication binds it to the hash attested in the verified `envelope.sent` audit payload and fails closed on mismatch (including a send event that attests a hash the pinned revision does not bind, or a pinned hash with no attested send hash). Manifest content deliberately excludes names, email addresses, labels, raw field values, token or capability material, object storage keys, key IDs, and provider identifiers or secrets.

The audit proof reads at most 5,000 audit events for the envelope, under a bounded aggregate payload byte budget, and fully re-derives the chain rather than trusting stored hashes: for each event it requires a known event type from an explicit allowlist (an unknown type fails closed), canonical `payload_json` (`JSON.stringify(JSON.parse(payload_json))` must equal the stored string byte-for-byte), an actor type allowed for that event (v2 hashes include `hashVersion`, `actorType`, and `actorId` for every event, so operator events may be `user` or `agent`; v1 rows keep the historical exact-actor checks because those preimages omitted `actorType`, except `draft.revision_created`, whose v1 preimage already hashed actor fields), and a recomputed SHA-256 over the exact preimage the writer hashed. It also verifies sequence contiguity, the `previous_hash`/`event_hash` chain link between consecutive rows, and that the chain's terminal row is the envelope's own `envelope.completed` event; a gap, a broken link, an unknown type, a wrong actor type, a non-canonical payload, or a wrong terminal event fails the publication closed as a genuine integrity error. Exceeding the event-count bound or the aggregate payload byte budget instead fails closed as the distinct, non-retryable `completion_artifact_evidence_too_large` outcome — an oversized envelope is an operational scaling signal, not evidence of tampering, and is never conflated with `completion_artifact_evidence_invalid`; the same too-large/invalid split applies to the manifest's document, recipient, and field counts and to its own source and gzip byte limits. PostgreSQL reads `occurred_at` at full microsecond precision and requires the sub-millisecond remainder to be exactly zero before use, so a sub-millisecond alteration below the driver's own millisecond-only rounding cannot silently pass; D1 requires the stored value to already be a canonical ISO-8601 millisecond string. The recipient roster is cross-checked for exact set equality — no row inserted, missing, or drifted in role or routing order — against the `{id, role, routingOrder}` triples declared by the envelope's one `envelope.ready` event. The complete `field_value` set is cross-checked against the union of `payload.fields` declared across every verified `recipient.signed` event — an inserted, deleted, or substituted row fails closed. Every actionable (signer/approver) recipient must carry `status = 'completed'` and a decision of the role-specific type — a signer's `decisionEventId` must resolve to a verified `recipient.signed` event and an approver's to a verified `recipient.approved` event, one can never stand in for the other — with a matching actor and timestamp, rather than trusting an unverified subselect; a non-actionable (viewer/prefill/cc) recipient must carry no signed or approved decision at all. None of this is a tamper-proof guarantee: an adversary with direct database write access who rewrites every event in the chain and recomputes every hash consistently would still pass. Detecting that class of whole-chain rewrite needs an external signed/published anchor (for example, a hash checkpoint written to a separate, append-only system) and remains out of scope.

The manifest is serialized as deterministic fixed-key JSON and rendered into a deterministic Markdown summary of the same fields, gzip-compressed with the existing fflate `level: 9, mtime: 0` convention used by the draft Git archive, and bounded in both source and compressed size the same way draft archives are — exceeding either bound is the same non-retryable `completion_artifact_evidence_too_large` outcome as the manifest's own count bounds, never `completion_artifact_evidence_invalid`. Both artifacts are written through the existing `ObjectStore.putImmutable` under content-addressed keys derived from their own gzip SHA-256. A failed write is resolved into exactly one of three outcomes by reading the object back and independently verifying its byte length and SHA-256, exactly like immutable draft archive persistence: bytes that verify mean the write already landed and are safely reused; an object that is missing, or that cannot be read back at all, is treated as a transient condition and the original error is rethrown for the caller to retry; an object that exists at that exact content-addressed key but holds different bytes is a real conflict — content-addressing makes that cryptographically impossible for honest data — and fails closed immediately as a non-retryable integrity error rather than retrying until attempts exhaust. Because the manifest is rebuilt deterministically from otherwise-immutable evidence, a retry after an object write succeeds but the SQL publish fails reproduces byte-identical artifacts and the same content-addressed keys.

Publication itself is one immutable pointer per envelope, enforced by a `(organization_id, envelope_id)` primary key. PostgreSQL locks the envelope row and then the job row, rechecks `status = 'completed'`, `sent_commit_sha = repository_head` and equal to the pinned value, the expected field generation, and that the audit chain is still anchored with `envelope.completed` as the immediate predecessor of the new event and nothing newer, before inserting the pointer, marking the job published, and appending a chained `envelope.completion_artifact_published` audit event in one transaction. D1 performs the equivalent recheck inside a rollback-on-failed-predicate command trigger. If the same evidence is republished under an already-used lease, the durable receipt for that envelope is compared field-for-field against the freshly recomputed command; identical evidence replays safely, while any difference is a fail-closed integrity error rather than a silent overwrite. When D1's trigger rolls an insert back, an absent durable receipt does not by itself prove which predicate failed — it could equally be an unrelated transient D1 error — so the store directly re-evaluates the same envelope-state, anchor, and lease predicates the trigger checks, classifying the outcome as stale or integrity only when one of them actually fails; it never inspects the error's message. When every predicate still holds, the original error is rethrown for the service to schedule a retry instead of recording a permanent integrity verdict.

Operators read publication state through `GET /api/v1/envelopes/{envelopeId}/completion-artifact`, an organization-authorized, explicit-allowlist read that returns only the publication status and the manifest/JSON/Markdown content digests (comparable to the existing draft `archiveSha256` exposure) — never object storage keys, audit event hashes, recipient email/name, raw field values, capability material, or internal claim tokens. `POST /api/v1/system/completion-artifacts/drain` reuses the existing `DELIVERY_WORKER_SECRET` constant-time bearer convention rather than a new credential. Cloudflare's existing one-minute scheduled trigger invokes it in-process through the Worker's own `fetch` handler alongside the invitation drain, with no Cloudflare REST API call from the Worker; Node/Docker drains it from the same host scheduler used for invitation delivery.

CC recipient delivery, public artifact grants, and completion notification mailing are implemented in Slice B (below). Operator commit-pinned DOCX export is a separate derived read (`GET /api/v1/envelopes/{envelopeId}/docx`) and is not part of the completion artifact. Operators and agents with `envelopes:read` download published JSON or Markdown evidence from `GET /api/v1/envelopes/{envelopeId}/evidence` (aliased at `.../completion-artifact/evidence`; `?format=markdown` selects Markdown, otherwise JSON) and the visual completion PDF from `GET /api/v1/envelopes/{envelopeId}/pdf` (aliased at `.../completion-artifact/pdf`). Cryptographic PDF certification/sealing (PAdES) of the completion package remains backlog.

## Completion artifact delivery and public access (Slice B)

Completion artifact delivery notifies agreement participants when an envelope completes and distributes purpose-separated read grants for the immutable completion artifact.

Artifact publication (Slice A) is a strict prerequisite: a periodic reconciliation worker discovers `completed` envelopes only after their completion artifact has been successfully published to object storage and recorded in the database. Envelopes lacking a published artifact are excluded from discovery and cannot enroll deliveries.

Delivery targets all participants in the completed agreement: `signer`, `approver`, `viewer`, and `cc` recipients are eligible for completion delivery. `prefill` recipients are strictly excluded, as prefill is pre-send authoring metadata and plays no role in post-completion artifact distribution. Each eligible recipient is enrolled exactly once in a dedicated `completion_delivery_outbox` table, guarded by a `UNIQUE(organization_id, envelope_id, recipient_id)` constraint and composite foreign keys to both `completion_artifact` and `recipient`.

Each enrolled recipient receives a high-entropy 32-byte `skca1_` access token grant. These grants are strictly purpose-separated: they convey read-only access to the published completion artifact, carry no signing or approval authority, cannot mutate any envelope state, and never mint or interact with browser session cookies. Grants carry an immutable 30-day lifetime (`access_expires_at = enrolled_at + 30 days`). When queried after expiration or after access has been revoked, the service returns an opaque RFC 9457 404 not-found response, indistinguishable from an unknown token, to prevent token enumeration or status oracle leakage.

Delivery is managed through a dedicated `completion_delivery_outbox` table, completely separated from the invitation `delivery_outbox`. Claiming follows a bounded-batch (at most 25 items per claim), stable-ordering, five-minute lease-reclaim, and capped exponential backoff (up to 10 attempts) pattern. The worker re-reads the current lease-scoped recipient/envelope projection immediately before decrypting token ciphertext and dispatching email. As with invitation delivery, external mail dispatch (`SIGNKIT_MAIL_PROVIDER=cloudflare`: the native Email Sending binding on Cloudflare Workers, its REST API on Node/Docker and Vercel; `SIGNKIT_MAIL_PROVIDER=smtp`: a generic SMTP client on Node/Docker and Vercel only — SignKit intentionally supports only the native EMAIL binding on Workers and does not bundle or support a Worker SMTP client) is non-transactional with respect to database updates; provider acceptance and database update form an at-least-once boundary, so downstream mail recipients must tolerate rare duplicates resulting from ambiguous process failures.

Ciphertext lifecycle and terminal failure semantics enforce least privilege:

- Upon successful delivery (provider acceptance), the sealed token ciphertext is scrubbed to `NULL` in the database, while the access grant remains active (`access_revoked_at IS NULL`) for the remainder of its 30-day lifetime.
- Upon permanent terminal failure (e.g. invalid recipient address, attempt exhaustion, or ciphertext digest mismatch), the sealed token ciphertext is scrubbed to `NULL` and access is terminally revoked by recording `access_revoked_at = now()`.
- Upon retryable failure (e.g. rate limits or transient mail transport errors), the sealed token is retained for exponential backoff retry and access remains active (`access_revoked_at IS NULL`).

Public artifact retrieval is exposed over two unauthenticated public boundaries requiring no cookies, sessions, or d6e-auth credentials:

- `GET /api/v1/completion-artifacts`: Accepts an `skca1_` token via `Authorization: Bearer <token>` and defaults to JSON (`application/json`).
- `GET /c/{token}`: Direct browser/link access accepting the token as a URL path parameter and defaulting to Markdown (`text/markdown`).
  Both endpoints support an explicit `?format=json`, `?format=markdown`, or `?format=pdf` query parameter. The resolver validates token structure and SHA-256 hash against the delivery grant and retrieves the matching object from immutable storage after verifying the recorded digest. JSON and Markdown are gzip-compressed text artifacts that are decompressed under a bounded byte budget; `pdf` returns verified `application/pdf` bytes from `completion_artifact_pdf` (D1 `0035_completion_artifact_pdf.sql`, Postgres `0033_completion_artifact_pdf.sql`) and is opaque 404 when that row has not been published. Storage bucket keys, tenant IDs, recipient identities, and internal metadata are never reflected in the response or error bodies.

Published artifacts in object storage and SQL pointer records in `completion_artifact` and `completion_delivery_outbox` are retained while SQL still references them. Unreferenced object-store uploads (failed CAS leftovers, not live pointers) are reclaimed by the bounded orphan sweep after a 24-hour grace period. Operator revocation UI and cryptographic PDF certification/sealing of the completion package remain deferred.

Node/Docker and Cloudflare Workers runtime profiles are fully supported; Vercel uses the existing PostgreSQL and S3-compatible path. Host schedulers invoke the protected `POST /api/v1/system/completion-deliveries/drain` endpoint using constant-time `DELIVERY_WORKER_SECRET` bearer validation; Cloudflare Workers drain completion deliveries in-process within `scheduled()` via `context.waitUntil` following invitation and completion artifact drains.

## Recipient capability reissue

Recipient capability reissue is implemented via `POST /api/v1/envelopes/{envelopeId}/recipients/{recipientId}/reissue` (and `POST /api/v1/envelopes/{envelopeId}/reissue`). It satisfies the following normative rules governing the issuance ledger, delivery worker, and view-continuation semantics so that reissuing never silently redefines what a "capability" or a "view" means.

A recipient is one stable identity for the life of an envelope. Reissuing invitation delivery to that recipient — because a link expired, delivery failed terminally, or an operator asks to resend — never creates a new recipient or a new envelope-recipient graph entry; it produces a new capability for the existing recipient row. Capabilities for one recipient form an append-only lineage: each new capability records the specific predecessor it supersedes, and at most one capability in that lineage is ever live — resolvable, non-revoked, non-expired — at a time. Superseding the old capability and minting the replacement happen atomically; there is no window where two capabilities for the same recipient both resolve.

The first-view evidence recorded in `recipient_viewed_command` and the `recipient.viewed` audit event is immutable and permanently bound to the capability that actually performed that first view. Reissuing a capability never rewrites, re-attributes, or duplicates this evidence, and reissuing is never itself a second view: it is a separate, repeatable operator command with its own audit event. That event follows the same PII- and secret-minimization discipline as every other event in this contract: its public payload may include only the recipient ID, a stable reason code, and timestamps, plus existing non-secret workflow metadata already carried by comparable events where essential; it must never contain raw tokens, capability hashes or other capability identifiers, ciphertext, key IDs, or delivery/outbox IDs. Distinguishing the historical capability that performed the first view from the capabilities that later superseded it is the job of the immutable command receipt and the issuance ledger — both server-side, non-public records — never the public audit payload.

A newly issued capability may be treated as continuing a previously viewed recipient — meaning the browser can proceed toward signing without repeating `POST /api/v1/signing/viewed` side effects — only when the durable issuance ledger proves an unbroken lineage from the historical capability that recorded `recipient_viewed_command` through every intermediate supersession to the capability currently presented. Lineage continuation is never an assumed replay and never silently granted; it must be positively proven from the issuance ledger on every request, not cached or inferred from cookie state alone.

The exact outcome for a presented capability depends on both liveness and lineage, and the atomic reissue slice must not blur together the different failure shapes involved. A token that is not live — its hash matches no current live capability, it is revoked, or it is capability-expired with nothing superseding it — resolves the existing opaque `not_found`, exactly as an unrecognized or non-live hash already does today; that path is unaffected by reissue and stays `not_found`. A live token whose recipient is not yet `viewed` is an ordinary first view or an ordinary idempotency-key replay, unaffected by reissue. A live token whose recipient is already `viewed` and whose lineage back to the capability that recorded `recipient_viewed_command` is proven by the issuance ledger results in continuation: the recipient proceeds without a second `recipient.viewed` event and without the request being recorded as an idempotency-key replay. A live token whose recipient is already `viewed`, where the presented capability genuinely is the current live successor but its lineage to the capability that recorded the view cannot be proven, results in `integrity_error`. This is a new check the atomic reissue slice must add, not a relabeling of today's `not_found` path: today, with no lineage to check at all, a capability that is not the recipient's sole live capability simply fails the live-capability lookup and is `not_found`, and that stays true — the new `integrity_error` branch only ever applies once the presented token has already been confirmed live. The pre-existing `integrity_error` case — a `viewed` recipient with no valid command or audit evidence at all for the very capability presented — is unchanged and remains a separate, same-capability check; it is not the cross-capability lineage check reissue adds.

Lineage continuation is recorded distinctly from idempotency-key replay and must never be conflated with it. Exact-key replay of `POST /api/v1/signing/viewed` remains scoped only to the literal capability and idempotency key that produced the original `recipient.viewed` event and is unaffected by reissue. As established above, the distinction between the capability that actually viewed and the capabilities later reissued lives only in the immutable command receipt and issuance ledger, never in the public `recipient.capability_reissued` payload.

Recipient-session cookies are envelope-scoped: the cookie name embeds the UUIDv7 envelope ID (`signkit_recipient_{envelopeId}`), so two envelopes opened in separate tabs coexist and reload independently. Reissue of the same recipient still shares that envelope's one cookie rather than minting a second cookie or a per-tab session for that envelope, matching the `/s/<token>` model. HTTP cookies have no value-conditional delete: a `Set-Cookie` deletion for a given name and path always clears whatever the browser currently has stored under that name, regardless of which token the response-generating request itself read when it decided to delete. With one shared cookie name _per envelope_, a late-arriving denial response for a now-superseded token (H1) can therefore delete a cookie that a different, concurrent exchange of the replacement link (H2) already wrote for that same envelope, purely because of response arrival order — the two requests never coordinate, and the deletion is unconditional at the transport layer no matter how correctly the server-side check that produced it was scoped. A terminal or failed exchange for envelope A never names envelope B's cookie, so it cannot disturb a second tab. The only way to remove the same-envelope race is for every non-terminal recipient surface to become overwrite-only in the same atomic slice that ships reissue: invalid, unknown, expired, revoked, or superseded tokens, and every `not_found`, `context_mismatch`, `integrity_error`, and `unavailable` response, must emit no `Set-Cookie` deletion at all. An inactive cookie is left inert rather than actively cleared — presenting it still fails closed on durable re-resolution every time regardless of whether it was ever deleted — and it is retired only by its own bounded `maxAge` (the existing capability-expiry/30-day cap) elapsing, or by being wholesale overwritten once its holder completes a genuinely valid `/s` exchange for that envelope. Visiting a superseded `/s/{oldToken}` link must therefore never delete an existing cookie; only a successful, valid exchange overwrites the same envelope-scoped cookie name and path, which is safe because writing a known-good value never depends on first verifying what was previously stored. The reissue operator command itself writes no recipient cookie at all; only a subsequent recipient-initiated `/s` exchange ever does. Because the cookie for one envelope is shared across tabs of that envelope rather than scoped to one tab, a stale tab that has not itself exchanged any link can still observe a live replacement cookie on its very next request purely because a different tab already completed that exchange; that request must lineage-continue exactly as defined above rather than being treated as suspicious.

Terminal recipient responses are decline, approve, and sign; operator void is a separate organization-authorized command that revokes capabilities in the database but never holds or mutates the recipient browser cookie itself. Decline, approve, or sign completion may still deliberately expire or exchange only that envelope's active session cookie, including the declined `/s` cross-name swap that sets a separate envelope-scoped decline-receipt cookie and deletes a same-token live cookie. This remains safe only because reissue is defined above to reject already-`declined` and `completed` recipients: a terminal transition and a competing reissue can therefore never be issuing cookies for the same recipient at the same time, so there is no concurrent write for a terminal deletion or exchange to race against. If that precondition is ever relaxed so reissue can target a terminal recipient, every terminal surface must first become overwrite-only in the same way as the non-terminal surfaces above, before that relaxation ships. Active `/s` must not delete a same-envelope decline-receipt cookie. Terminal decline is irreversible, so there is no legitimate active-after-declined state. A live `/s` that already resolved can race a concurrent decline that has already persisted the receipt: the late `/s` response would then delete that receipt while setting an already-invalid live cookie. Leaving an old receipt cookie alongside an active cookie is safe: page load tries active durable authorization first and falls back to the receipt if that cookie is invalid. Exchanging envelope A never names envelope B's cookies.

Reissue eligibility must not conflate envelope-level terminal expiry with capability-level expiry, which are different things today. An envelope already in its own terminal `expired` state is rejected for reissue exactly like `voided` and `completed`, the same as every other still-deliverable invitation intent. Capability expiry is unrelated: every capability carries its own expiry timestamp, and a recipient whose most recent capability has simply expired while the recipient itself remains `pending` or `viewed` inside a `sent` or `in_progress` envelope is precisely the primary case reissue exists to serve, and must remain eligible. `pending` or `viewed` plus `sent` or `in_progress` is necessary but not sufficient, though: a recipient in a later, not-yet-released routing group is also `pending` with a reserved capability, but that capability was never activated — its durable `recipient.capability_expires_at` is still `NULL` and its outbox row is still `blocked` — precisely because release, not reissue, is what turns a blocked future-routing reservation into a live, expiring link. Reissue therefore additionally requires that the targeted recipient has been released at least once: durable `recipient.capability_expires_at IS NOT NULL`, whether that expiry is now in the future or already in the past, and the invitation it would supersede is not merely a blocked, reserved future-routing intent. A recipient whose group has never been released is rejected without mutation; only the normal routing-release transition performed by approval or signing can make it eligible, never reissue. The full eligibility rule is therefore: the envelope must be `sent` or `in_progress`; the recipient must be `pending` or `viewed`; and the recipient must already have been released, meaning `recipient.capability_expires_at IS NOT NULL` and its current outbox row is not a still-blocked future-routing reservation. Once release has occurred, whether that capability now happens to be still live, capability-expired, or revoked is irrelevant to eligibility and affects only which capability the new one supersedes; a still-`blocked` recipient is never eligible, because minting a new expiry for it would make its link resolvable before its order opens.

The transaction boundary matches the existing decline/void/approve pattern rather than introducing a new one. PostgreSQL locks the envelope row, then the target recipient row, then the recipient's existing outbox row(s), in that stable order inside one transaction, before superseding the old capability, inserting the new capability and a new delivery outbox row, and appending the reissue audit event. D1 performs the same sequence behind one command insert and a rollback-on-failed-predicate trigger, so supersession, new-capability insertion, new-outbox insertion, and audit append either all become visible together or none do. As with decline and void, a `processing` delivery lease observed on the recipient's current outbox row before publication fences the entire reissue with a retryable conflict and no partial write, so a reissue can never race an in-flight provider submission for the capability it is about to supersede. The release predicate above — recipient status, `capability_expires_at IS NOT NULL`, and an outbox row that is not still `blocked` — is rechecked inside this same atomic boundary alongside the lease fence and the capability-supersession CAS, not as a separate earlier check: PostgreSQL rechecks it under the recipient row lock immediately before superseding, and D1's rollback-on-failed-predicate trigger guards it as one of the same predicates. Reissue evaluates that predicate atomically under its own publication boundary: if it observes the recipient still unreleased, it fails closed with no mutation, exactly as above. If a concurrent routing-group release instead commits first, reissue then observes an already-released recipient and may legitimately proceed as an ordinary already-released reissue — the two commands are never interleaved and no execution can publish a reissued live capability before the routing release that made the recipient eligible; each recheck simply sees whichever fully committed state existed first.

Reissue must never overwrite delivery outbox history. Each reissue creates a new outbox row for the new capability rather than mutating or deleting the prior row; delivered and already-permanent-failure evidence on earlier rows remains exactly as retained today. This is required so a future implementation can represent distinct invitation attempts or issuances as an ordered sequence of outbox rows per recipient, not a single mutable slot.

This landed as an atomic feature slice: the issuance ledger (`migrations/d1/0036_capability_reissue.sql`, `migrations/postgres/0034_capability_reissue.sql`), the reissue command itself, append-only delivery outbox changes, lineage-aware view continuation in the viewed-recording path, the overwrite-only failure-response rule for non-terminal surfaces, and D1/PostgreSQL parity suites.

Acceptance-test contract enforced by the test suite:

- Reissuing an already-released, `pending`, not-yet-viewed recipient (`recipient.capability_expires_at IS NOT NULL`) mints one new live capability, supersedes the old one, leaves the recipient `pending`, appends one `recipient.capability_reissued` event whose public payload contains only the recipient ID, reason, and timestamps, and makes the old link resolve `not_found`.
- Reissuing a recipient who has already been released at least once (`recipient.capability_expires_at IS NOT NULL`) and whose current capability has simply capability-expired, while the recipient remains `pending` or `viewed` and the envelope remains `sent` or `in_progress`, is accepted; reissuing a recipient inside an envelope-terminal `expired`, `voided`, or `completed` state, or a `declined` or `completed` recipient, is rejected without mutation.
- Reissuing a `pending` recipient in a later, not-yet-released routing group — `recipient.capability_expires_at` still `NULL` and its outbox row still `blocked` — is rejected without mutation regardless of envelope state; only the normal routing-release transition performed by approval or signing can make that recipient eligible, never reissue.
- A routing-group release and a concurrent reissue attempt racing the same recipient never interleave: the D1 trigger and PostgreSQL transaction recheck the release predicate atomically with status, lease, and the capability-supersession CAS; reissue fails closed with no mutation if it observes the recipient still unreleased, and may otherwise proceed as an ordinary already-released reissue if the release fully committed first, but no execution ever publishes a reissued live capability ahead of the routing release itself.
- A live replacement capability presented for an already-`viewed` recipient with intact lineage results in continuation: no second `recipient.viewed` event, and the request is not recorded as an idempotency-key replay.
- A live capability presented for an already-`viewed` recipient whose lineage back to the capability that recorded the view cannot be proven results in `integrity_error`, with no `Set-Cookie` in the response.
- A token that is not live at all (unknown hash, revoked, or capability-expired with nothing superseding it) results in `not_found`, with no `Set-Cookie` in the response; the existing cookie, if any, is left completely untouched.
- Every non-terminal denial or error outcome — `not_found`, `context_mismatch`, `integrity_error`, and `unavailable` — emits no `Set-Cookie` deletion under any circumstance.
- Race ordering: an old-capability request (H1) begins, a concurrent valid replacement-link exchange (H2) completes and sets the live cookie, and H1's denial response arrives after H2's; H1's response carries no `Set-Cookie`, so H2's cookie survives untouched.
- Cross-tab: after one tab exchanges a valid replacement link and the shared cookie is updated to the new live token, a second, stale tab for the same recipient that has not itself exchanged any link observes that same live cookie on its next request and must lineage-continue rather than erroring.
- The reissue operator command's own response never sets or clears any recipient browser cookie.
- Published/replayed decline, approve, and sign retain current terminal cookie expiry/exchange behavior, and tests prove reissue rejects the same completed/declined recipient so no live successor can race it.
- Exact idempotency-key replay of the reissue command itself returns the original receipt without minting a second lineage entry or a second outbox row.
- A `processing` lease on the current outbox row fences a concurrent reissue attempt with a retryable conflict and no partial state.
- D1 and PostgreSQL produce an identical resulting projection — recipient status, live capability, full outbox row history, and audit sequence — for every scenario above.

Non-goals: bulk or multi-recipient reissue in one command; changing a recipient's identity, email, or role (reissue only replaces the capability, never the recipient row it belongs to); retroactively altering or deleting any existing `recipient.viewed` or delivery audit evidence; and any UI, copy, or notification design. Recipient capability reissue is also unrelated to sealing-key rotation (tracked separately, issue #10): rotation re-encrypts existing outbox ciphertext under a new deployment secret without changing which capability is live or minting a new token, and can happen with or without any reissue ever occurring; reissue mints an entirely new capability and token and never re-encrypts or reuses old ciphertext.
