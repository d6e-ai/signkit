# 全体を対象にした最小限のリファクタリング

Date: 2026-10-11

Status: accepted — 計画範囲の選択。実装の完了を示すものではない。

## Context

2026-10-05と2026-10-10の提案は、readyの縦切りを起点にR0〜R7で権限・正本・job・wire契約まで段階移行する計画だった。
全体を理想的な境界へ揃える範囲は大きく、20〜35人日の概算になった。
ユーザーは対象をreadyへ限定することではなく、全体を対象にした最小限の変更を求めた。
最新の手元のHEAD `189cc55996a041dec9cc89e5bf67648623c8daf8` には#217・#219・#218の挙動修正が含まれる。
これらは残す既存契約であり、構造整理の達成とは数えない。

## Decision

[計画](../refactoring-plan.md)、[責務](../refactoring-boundaries.md)、[検証](../refactoring-verification.md)を、全体対象の軽量版へ置き換える。
旧R0〜R7の段階・工数・全面移行の完了条件は今回の実施範囲として採用しない。
すべての機能を点検し、根拠のある重複と別機能runtimeへの不自然な依存だけを変更する。

1. 操作固有のfingerprint/監査/receiptとsign/approveの共通routing判断。
2. 共用DB/ObjectStore/文書engineの組み立てと、別機能runtimeの借用。
3. 同じ意味のバイト検証・不確実な不変保存確認・backoff計算。
4. UIの通信/同じキーでのretry/receipt確認と、変更したHTTP/OpenAPI/Rust契約の適合。

目安は4つのPR群・7〜12人日。テストとレビューを含む概算であり、PR数の上限やAIの実時間ではない。
権限/成果物の新しい型体系、汎用job/DI、全schema/code generation、全テストの書換えを必須にしない。
API、SQL/schema、監査・receipt・文書形式、描画、公開順序、job/lease/GC、認可とconsentは維持する。

## Verification boundary

既存テストを残し、対象の固定fixture、競合・部分失敗・再送、実runtimeの必要な確認だけを補う。
未充足のWorkers製品E2Eと大容量CPU/メモリ検証は未充足のまま明示する。
I/O・バッファ保持・描画・公開/実行方式の変更が必要なら別の変更へ分離し、対象のWorkers製品経路と資源予算の実証を要求する。
runtimeの入口変更をbuildだけで成功扱いしない。

## Consequences

現行のポート・型・テストを活かし、全体の保守負担を小さな変更で減らす。
全機能を点検しても、すべてのファイルを変更しない。未調査を変更不要とせず、残す重複には具体的な理由を記録する。
理想的な全境界への移行、製品の残課題、実インスタンスへのデプロイは別の判断になる。
過去のADRは当時の理由を保存し、このADRによる範囲変更の案内を追加する。

## Rejected alternatives

- readyだけで終了する。対象を全体とする要求に合わない。
- 工数だけを減らし、旧R0〜R7の完了条件をすべて残す。範囲と見積もりが一致しない。
- フォルダ移動やファイル分割だけで完了とする。重複した判断と不自然な依存が残る。
- 検証を省いて小さく見せる。今回触る経路の再送・競合・バイト互換性は維持する。
