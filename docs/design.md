# SignKit design

Status: normative draft  
Last updated: 2026-09-12

## Product boundary

SignKit is a modular monolith for drafting, sending, signing, retaining, and automating agreements. It is not a d6e-specific workflow product: d6e can orchestrate work before and after signature through the same versioned API and webhooks available to every integrator.

The open-source core must remain useful on its own. Security and evidence collection are never paywalled. Enterprise licensing applies to higher-order integrations and policy features, not to the correctness of signatures or audit capture.

OpenSign and Documenso were inspected only as product references. Both repositories use AGPL-3.0 boundaries, and Documenso has separately licensed enterprise code. SignKit must use original code, names, schema, copy, and visual expression unless the project deliberately adopts compatible license obligations later.

## Architecture

```text
SvelteKit UI · REST API · public signing links · webhooks
                            │
                 application commands/queries
                            │
       envelope · draft Git · signing · audit policies
                            │
      ┌──────────┬──────────┼──────────┬───────────┐
      │ DB port  │ object   │ identity │ jobs/mail │
      ├ Postgres ├ S3       ├ d6e-auth ├ outbox    │
      └ D1       └ R2       └ guest    └ Queue     │
```

Runtime services are created from each SvelteKit request. Cloudflare bindings come from `event.platform.env`; request-scoped state is never held in module globals. The domain and application layers do not import a platform SDK.

## Envelope model

One envelope is one send operation. It contains one or more ordered Markdown documents, one recipient graph, fields, artifacts, an audit stream, and exactly one Git repository.

Core states are:

```text
draft → ready → sent → in_progress → completed
                    ├──────────────→ declined
                    ├──────────────→ expired
                    └──────────────→ voided
```

Only `draft` is mutable. `ready` can return to `draft` before sending. Sending atomically pins `sent_commit_sha`; later changes require a new or explicitly superseding envelope. Completion occurs only after every required recipient action has committed.

Recipient roles are `signer`, `approver`, `viewer`, `prefill`, and `cc`. Signer and approver are action-bearing. Viewer is a post-send read-only observer that must share an order with an action-bearing recipient and never blocks advancement. Prefill is pre-send-only; because its authoring command is not implemented, ready graphs containing prefill are rejected and it never receives a post-send capability. CC remains outside the signing capability graph.

The initial recipient mutation is deliberately tied to `POST /api/v1/envelopes/{envelopeId}/ready`. The command declares the complete graph, requires at least one signer or approver, rejects prefill and every viewer-only routing order, normalizes email addresses, rejects duplicates, and checks the expected Git generation. D1 publishes its command, `draft → ready` compare-and-set, recipient projection, and `envelope.ready` event in one batch; PostgreSQL uses a row lock and transaction for the same boundary. The replay receipt is stored without capability tokens, and the audit payload contains recipient IDs, roles, and routing order rather than names or email addresses.

Actual sending is a separate irreversible `POST /api/v1/envelopes/{envelopeId}/send` command. It requires the expected Git generation and ready audit event ID, atomically pins `sent_commit_sha`, reserves hashed capabilities only for signer, approver, and viewer recipients, and writes one durable delivery intent per reserved capability before changing `ready` to `sent`. The minimum action-bearing order and its co-routed viewers are `pending`; higher action-bearing groups and their viewers are `blocked` with no active expiry until release. Legacy prefill delivery rows are never claimable and are terminally scrubbed by the bounded cleanup sweep. CC delivery belongs to completion rather than the signing-capability graph.

The raw random capability exists durably only as AES-256-GCM ciphertext in the delivery outbox, sealed with a deployment secret and organization/envelope/recipient/outbox context as authenticated data. Recipient rows contain the SHA-256 hash; public responses and audit payloads contain neither token, hash, ciphertext, key ID, nor outbox ID. Every delivery intent is database-constrained to a recipient in the exact same organization and envelope: PostgreSQL uses a composite foreign key, while D1 uses insert/update guards and validates all existing rows during migration. The delivery worker decrypts immediately before delivery, verifies the ciphertext digest, sealing key, authenticated context, plaintext capability hash, expiry, and current recipient/envelope eligibility, and scrubs ciphertext after provider acceptance or a terminal failure. `envelope.sent` means that delivery intent is durable, not that an email provider has accepted a message. The caller-supplied ready audit event remains an immutable anchor for the same envelope, Git generation, and commit; `envelope.sent` chains from the current audit head, which may include later field-placement events. D1 uses a final publish guard to verify that anchor and the full outbox/capability projection before the state CAS and audit append; PostgreSQL uses row locks and one transaction. Provider delivery and routing-group release remain separate commands.

Invitation claims are limited to 25 rows, ordered by availability and creation, and guarded by a unique lease token. Pending and retryable failed rows become eligible at `available_at`; abandoned `processing` rows are reclaimed only after a five-minute lease. Each claimant re-reads its organization- and lease-token-scoped recipient/envelope projection immediately before decrypting or sending. The claim transaction also converts at most 100 now-ineligible due or abandoned rows per run into terminal failures and scrubs their ciphertext, using a partial cleanup index so a decline, completion, revocation, expiry, or envelope terminal transition cannot strand reusable token material indefinitely or create an unbounded periodic sweep. Completion and failure updates compare the organization, delivery ID, `processing` state, and lease token. Provider authentication, sender setup, unknown provider errors, transport failures, rate limits, and sealing-key drift remain retryable; only recipient-scoped permanent rejection, exhausted attempts, or integrity failures are terminal and scrub ciphertext. Retryable failures use capped exponential backoff for at most ten claimed attempts. A per-item store failure is isolated from sibling claims, while its lease becomes reclaimable after timeout. Cloudflare uses a one-minute scheduled trigger, D1, and the native Email Sending binding. Node/Docker exposes the same bearer-protected internal drain command for a host scheduler, backed by PostgreSQL and the Cloudflare REST adapter. Responses and logs allowlist only delivery IDs, aggregate outcomes, and stable error codes. The provider call remains non-transactional after that final state read, and the provider-acceptance/database-completion gap is explicitly at-least-once: a crash after provider acceptance can cause a later duplicate, so mail content and downstream integrations must tolerate it.

Operators read progress through organization-authorized `GET /api/v1/envelopes/{envelopeId}/deliveries`. Tenant scope comes only from the verified d6e-auth session. The response contains the envelope state plus recipient ID, role, routing order, delivery state, attempts, timestamps, and a sanitized machine error code; it omits recipient email/name, capability material, sealing metadata, provider credentials, provider response bodies, and internal outbox IDs.

`POST /api/v1/envelopes/{envelopeId}/fields` places signing fields while an envelope is `ready`, before it is sent. It is an idempotent, whole-set replace: the body carries the expected Git generation, an independent `expectedFieldGeneration` compare-and-set counter for the field set itself, and one to fifty declarations naming a recipient, a `documents/*.md` path, a field type (`signature`, `initials`, `text`, `date`, `checkbox`), a label, whether the field is required, and a semantic document-order `position`. This slice tracks reading order only; page and x/y geometry are deliberately out of scope. Only signer recipients scoped to the same organization and envelope may own a field, and every document path is validated against the exact bounded Git workspace pinned by the expected generation, reusing the same `DraftPersistenceService` read path as the draft endpoints rather than duplicating archive decoding. Field IDs are derived deterministically from the recipient, document path, field type, and position, so resubmitting the same declaration reproduces the same ID even if its label or `required` flag changed. Publishing atomically rechecks the envelope's `ready` state, Git generation and head, and field generation; replaces the entire `envelope_field` projection; increments `expectedFieldGeneration`; and appends one PII-minimized `envelope.fields_placed` audit event whose payload excludes labels. D1 uses a rollback-on-failed-predicate trigger — including a `json_each` check that every declared field's recipient is a signer in scope — gated by the same command-insert boundary as `ready`, with the field replacement itself performed as later statements in the same batch; PostgreSQL locks the envelope row and then every referenced recipient row in ID order inside one transaction before replacing the set. Fields are declared only in SQL; Git and object storage are never touched by this command. The response omits labels, audit hashes, archive/storage identifiers, emails, names, and internal command IDs.

## Draft Git repository

Tracked content is deliberately narrow:

```text
documents/<stable-document-id>.md
```

The database owns titles, ordering, recipients, field coordinates, state, and artifact references. Git never contains DOCX, PDF, signature images, access tokens, or evidence bundles.

Each edit performs these steps:

1. Read the current generation, archive key, SHA-256, and Git head.
2. Download the bounded compressed repository archive and verify its external SHA-256.
3. Restore a request-local in-memory filesystem and reject unsafe paths, excess files, and excess size.
4. Use `isomorphic-git` to edit, stage, and commit Markdown files with human/agent/system attribution.
5. Serialize sorted repository files and gzip them deterministically.
6. Upload to an immutable, content-addressed object key.
7. Publish the expected-generation pointer, durable idempotency result, and `draft.revision_created` audit event atomically in the database.
8. If publication loses a race, return a typed conflict; unreferenced content-addressed uploads are garbage-collected later and are never deleted on the request path.

Recommended key:

```text
draft-repositories/v1/organizations/{organization}/envelopes/{envelope}/sha256/{sha256}.git.gz
```

Git SHA-1 identifies revisions but is not the storage integrity boundary. Every archive and final artifact also has a SHA-256 digest. The current application service implements bounded archive reads, external SHA-256 verification, immutable object writes, and generation-based publication. `GET /api/v1/envelopes/{envelopeId}/draft` exposes normalized Markdown without leaking the internal object key or archive bytes. `POST /api/v1/envelopes/{envelopeId}/draft/commits` accepts one to fifty direct `documents/*.md` edits, requires an expected generation and idempotency key, and optionally records automation provenance. D1 uses a trigger-backed command table and PostgreSQL uses a row lock plus transaction so the pointer, replay result, and audit event become visible together. Streaming archive production, orphan collection, and broader recovery tests remain before production use.

## Persistence

The initial profiles are:

| Runtime     | Database   | Objects               | Background work                     |
| ----------- | ---------- | --------------------- | ----------------------------------- |
| Node/Docker | PostgreSQL | S3-compatible         | protected outbox drain + REST mail  |
| Cloudflare  | D1 binding | native R2 binding     | scheduled D1 outbox + email binding |
| Vercel      | PostgreSQL | external S3 initially | platform-specific                   |

D1 and PostgreSQL keep distinct migrations behind the same domain-shaped ports. The shared model avoids database enums, arrays, and mandatory JSON-specific column types. Every tenant-owned table carries `organization_id`; composite keys and foreign keys include it so rows cannot be linked across tenants accidentally.

SQL and object storage do not share a transaction. Objects are immutable; a successful SQL CAS publishes the new pointer. Failed uploads remain invisible and are safe for later orphan collection.

R2 is used through its in-process Worker binding, not the S3/REST endpoint. Node uses the S3 adapter. Native Vercel Blob is not S3-compatible and remains a separate future adapter.

## Authentication and authorization

The sender/admin UI uses d6e-auth authorization-code OAuth. Access tokens are verified with RS256, issuer `d6e-auth`, and audience equal to `D6E_AUTH_CLIENT_ID`. Tokens remain inside an AES-GCM-encrypted, `HttpOnly`, `SameSite=Lax` server cookie.

d6e-auth proves identity, not envelope or organization access. Active organization memberships are fetched server-side. Suspended and closed organizations are rejected. A remembered organization cookie is display state only. Every query and mutation must match the authorized organization and object ID.

Recipient signing uses a separate, narrow capability link: high entropy, one recipient, stored as a hash, expiring, revocable, rate-limited, and unable to call operator APIs. A recipient does not need a d6e account by default. `GET /api/v1/signing/context` resolves only a bearer capability and is independent from browser OAuth organization state. Its D1 and PostgreSQL queries require a non-null future expiry, no revocation, a `pending` or `viewed` non-CC recipient, a `sent` or `in_progress` envelope, and a composite organization/envelope join. The response is an explicit allowlist that excludes organization identity, recipient email/name, and all token material; all inactive capability cases share one not-found shape.

The human `/s/<token>` route is a no-store, no-referrer exchange rather than the persistent signing page. After resolving current durable state, it seals the raw token into an AES-256-GCM `HttpOnly`, `SameSite=Lax` cookie and redirects to `/{locale}/sign`. HKDF-SHA-256 derives a recipient-session subkey from the deployment session master key, while versioned additional authenticated data prevents cross-purpose ciphertext reuse. Cookie lifetime is bounded by both the durable capability expiry and 30 days. The clean page decrypts server-side and re-resolves the database on every request; invalid or definitively inactive cookies are deleted, while transient persistence failures preserve them for retry. A failed or attacker-controlled new link never clears a previously valid session. Operator OAuth resolution is skipped for every recipient surface.

Recipient document reads resolve the pinned revision only from the active capability query. That query joins the tenant-scoped envelope to its `sent_commit_sha` revision command and requires the current immutable pointer to match the send pin; clients never submit an envelope ID, commit, object key, or path. The server reconstructs the content-addressed key, bounds the compressed archive and decoded gzip, recomputes SHA-256, requires Git HEAD to equal the send pin, and rechecks capability authorization immediately before disclosure. The browser renders a server-produced, sanitized CommonMark surface with GFM tables, strikethrough, autolinks, and task-list syntax. Raw HTML is disabled before conversion and the generated tree passes through an explicit allowlist that contains no image or active-content elements. Markdown images become inert alt-text notices, only absolute HTTPS and `mailto:` links remain interactive, HTTPS links open in a new tab with `noopener noreferrer`, and email links delegate to the user's mail handler without opening a blank tab. Bidi and other invisible formatting controls are replaced by visible `U+` markers in the formatted view while ordinary RTL text remains intact; an exact escaped Markdown-source tab remains available for verification. Rendering rejects more than fifty documents, more than 1 MiB of total source, a document over 512 KiB, a syntax tree deeper than 64 levels, or more than 50,000 syntax nodes. A global SvelteKit CSP additionally limits scripts, frames, objects, connections, forms, fonts, media, workers, and images to the minimum first-party surface. The bearer `GET /api/v1/signing/documents` endpoint returns the same allowlisted context and raw documents without organization, recipient identity, archive, digest, token, storage details, or generated HTML. This read path adds no view or audit mutation. Every later signing mutation decrypts the currently active cookie, re-resolves durable capability state, and treats submitted envelope and recipient IDs only as equality constraints, so replacing recipient A's cookie with recipient B's cannot authorize a stale A tab.

The browser records a recipient view only through `POST /api/v1/signing/viewed` after the page is foreground-visible; link exchange, page load, prefetch, and document `GET`s remain read-only. The encrypted recipient cookie is the sole authority. Submitted envelope and recipient IDs are equality constraints against a fresh capability resolution, never alternate authority, and the endpoint accepts only exact same-origin requests. One idempotency key is scoped to the resolved recipient; a safe replay must match both the normalized request fingerprint and its stored audit evidence.

Publishing the first view changes the recipient from `pending` to `viewed`, may change its envelope from `sent` to `in_progress`, stores a durable command receipt, and appends a PII-free `recipient.viewed` audit event as one atomic database operation. PostgreSQL locks the envelope before the recipient and rechecks the capability, pinned revision, and audit head inside a transaction. D1 inserts the command through a trigger whose guarded recipient/envelope updates and audit insert roll back together on any failed predicate. A recipient already marked viewed without matching durable command and audit evidence is an integrity failure rather than an assumed replay. Revocation, expiry, recipient switching in another tab, audit-head races, and state drift are rechecked at publish and again before the response is disclosed.

Recipient decline is a separate explicit `POST /api/v1/signing/decline` confirmation, available only to an active signer or approver. It uses the encrypted recipient cookie as sole authority and treats submitted IDs only as equality constraints. Because success immediately makes the capability inactive, the decline store resolves identity by capability hash and owns both active publication and terminal replay verification; it does not depend on the active-access resolver after commit. One atomic publication marks the actor and envelope `declined`, revokes every other issued non-completed capability without changing sibling recipient statuses, terminally fails pending, blocked, and retryable-failed invitation intents, scrubs their sealed capability ciphertext, stores a durable command receipt, and appends one PII-free `recipient.declined` event. The receipt and audit payload contain the same sorted IDs of only the sibling capabilities actually revoked plus the stable `envelope_declined` reason; they never contain names, email addresses, capability hashes, ciphertext, key IDs, or outbox IDs. Existing delivered and permanent-failure evidence remains unchanged. D1 uses one command insert plus a rollback-on-failure trigger; PostgreSQL locks the envelope, every recipient, and every delivery row in stable order. A `processing` delivery lease observed before publication fences the entire decline with a retryable 409 before any mutation, so no new provider submission begins after the terminal commit; provider calls already accepted outside the database retain the documented at-least-once limitation. If that lease clears after a D1 trigger rollback but before failure classification, the safe fallback is an unavailable response with no mutation and no cookie clearing; retrying the command is safe. An exact evidence-checked replay succeeds after response loss only under the original idempotency key; version 1 receipts remain replayable after migration, while every new command uses version 2 revocation evidence. Version 2 replay also verifies the current sibling-revocation and scrubbed-delivery projection, so later authority drift fails closed. A fresh key presented after revocation receives the same opaque not-found outcome as other inactive capabilities. Mismatched tabs, inactive or non-actionable capabilities, key reuse, audit races, manifest drift, and partial terminal state fail closed. Successful and replayed browser responses replace the active capability cookie with a separately derived AES-GCM terminal-receipt cookie; cookie publication must succeed before the active cookie is removed, so a failed exchange remains safely replayable.

The terminal decline receipt is a read-only authorization boundary, not a weakened active recipient session. Its encrypted locator contains the organization, envelope, recipient, original idempotency key, capability hash, and fixed `declinedAt + 30 days` expiry, but the public page returns only envelope/recipient IDs, both declined statuses, the timestamp, and locale. Every reload re-proves the command request fingerprint, the `recipient.declined` audit event and immediate predecessor, and the current revoked/scrubbed terminal projection in D1 or PostgreSQL. The original `/s/{capability}` URL can perform the same evidence-checked recovery after response loss; a successful new active link deletes any stale receipt cookie. Expired, malformed, unrelated, superseded, or projection-drifted locators share the inactive result and are deleted, while transient persistence failures preserve the cookie for retry. This path never invokes the document workspace service, Git archive, R2/S3, or recipient mutation endpoints, and the authoritative declined UI has no document or field branch in its server data or DOM.

Operator voiding is an organization-authorized `POST /api/v1/envelopes/{envelopeId}/void` command for `draft`, `ready`, `sent`, and `in_progress`. The request supplies both expected status and expected Git generation, so a stale confirmation or automation run cannot silently void a concurrently committed or sent envelope. The audit payload binds the previous status, generation, nullable repository head and sent pin, timestamp, and exact sorted IDs of capabilities revoked with reason `envelope_voided`; it excludes names, email addresses, capability hashes, ciphertext, key IDs, and delivery IDs. Publication uses the same terminal delivery boundary as decline: any `processing` lease fences the command; pending, blocked, and retryable-failed invitations become permanent terminal failures with ciphertext scrubbed; delivered and already-permanent evidence remains unchanged; every issued non-completed capability is revoked without changing recipient statuses. D1 performs this behind one rollback-on-failure command trigger, while PostgreSQL locks envelope, recipients, and delivery rows in stable order and verifies exact updated ID sets. The envelope transition, cleanup, revocation, receipt, and `envelope.voided` audit append are atomic. Exact-key replay rehashes receipt and audit evidence and rechecks the current terminal projection; fresh keys on terminal envelopes are rejected. If a D1 processing lease disappears between trigger rollback and failure classification, the conservative response is unavailable and a retry is safe. Undo, free-form reasons, object deletion, accepted-message cancellation, and role-specific organization RBAC are out of scope.

Recipient approval is a separate explicit `POST /api/v1/signing/approve` confirmation, available only to an active approver who has already viewed the documents. It uses the encrypted recipient cookie as sole authority and treats submitted envelope/recipient IDs only as equality constraints; same-origin, a required bounded idempotency key, `application/json`, and a 4 KiB body cap are all enforced before the cookie is read. One atomic publication marks the actor `completed`, revokes its capability, and appends a `recipient.approved` audit event. Signer and approver roles are the action-bearing workflow participants; viewer and prefill roles never block routing-group release or envelope completion. If signer or approver actions remain in a later routing order once the acting group clears, the same publication releases the next actionable order's reserved capabilities to a bounded expiry and reopens matching blocked delivery-outbox rows, including non-CC observers co-routed at that order, while leaving recipient statuses untouched. If no signer or approver action remains outstanding, the publication instead completes the envelope: `envelope` moves to `completed` and a second, deterministically chained `envelope.completed` audit event is appended in the same publication, its `previousHash` equal to the `recipient.approved` event's own hash — a two-event hash chain rather than a separate command. D1 uses one command insert plus a rollback-on-failure trigger that performs the actor update, the conditional group release or completion, and both audit inserts; PostgreSQL locks the envelope, every recipient, and the delivery outbox in stable order inside one transaction. The application layer retries only a bounded audit-head race with a fresh timestamp; every other terminal outcome (not found, context mismatch, role not actionable, idempotency conflict, integrity error) is returned unchanged on the first attempt. Exact evidence-checked replays succeed after response loss only under the original idempotency key, including when a later action has since advanced the envelope from `in_progress` to `completed`; a fresh key after revocation returns opaque not-found. The browser response clears the recipient session cookie only after a published or safely replayed approval; every other outcome, including a currently inactive or not-yet-eligible capability, leaves the cookie in place so an ambiguous or racy denial can never itself destroy a session a later request might still resolve.

Under this role contract, a released non-CC observer means `viewer`; prefill never enters the post-send graph. Final approval has an additional terminal boundary: before `envelope.completed`, any `processing` invitation lease fences the command with a retryable conflict. Otherwise pending, blocked, and retryable-failed invitations become permanent terminal failures with ciphertext scrubbed, and every outstanding issued non-completed capability is revoked without changing recipient status. Delivered and already-permanent evidence remains unchanged. D1 performs this in the command trigger and PostgreSQL under the existing ordered locks; completion replay also verifies that this terminal projection has not regained authority.

Recipient signing is a separate explicit `POST /api/v1/signing/sign` confirmation, available only to an active signer who has already viewed the documents. The encrypted recipient cookie remains the sole authority; submitted envelope/recipient IDs and `expectedFieldGeneration` are equality/CAS constraints against a freshly resolved capability and the current field-generation pointer, so a stale page cannot sign after labels or required flags change. Same-origin, a required bounded idempotency key, `application/json`, and a 2 MiB body cap sized for the maximum valid field set are enforced before the cookie is read. The body supplies exactly one value for every field this recipient owns, including the exact empty set when none are assigned: typed signature/initials, text, a real `YYYY-MM-DD` calendar date, or a boolean checkbox. Values are normalized (trim, type, calendar validity) before the request fingerprint is hashed, together with field generation, so equivalent submissions hash identically regardless of value order. Durable replay reconstructs that fingerprint from stored `field_value.value_json` rows and fails closed if the digest, audit chain, or one-shot field set cannot be proven. Raw values and labels are written only to SQL; `recipient.signed` carries value SHA-256 digests, and the public receipt never echoes values, labels, audit hashes, or capability material. One atomic publication completes the actor, revokes its capability, inserts immutable field values, pins the sent commit and field generation, and either releases the next signer/approver order with its co-routed viewers or performs the same lease-fenced terminal cleanup as approval before completing the envelope with a chained `envelope.completed` event. D1 inserts the command through a rollback-on-failed-predicate trigger, then inserts `field_value` rows as later statements in the same batch; PostgreSQL locks the envelope, recipients, delivery outbox, envelope fields, and existing field values in stable ID order inside one transaction. Only the original idempotency key can recover an evidence-checked terminal receipt after response loss; a fresh key after revocation returns opaque not-found. Ink, PDF, DOCX, webhooks, and rate limits are out of scope.

Agents and the future CLI use revocable organization-scoped workload credentials with explicit scopes such as `envelopes:read`, `drafts:write`, and `envelopes:send`. They never use browser cookies or the OAuth client secret.

## Recipient capability reissue (design contract, not implemented)

This section is a design contract, not a shipped feature: no resend or reissue endpoint exists in the API today. It fixes the semantics that a future issuance ledger, delivery worker, and view-continuation change must satisfy before any of that code lands, so implementation cannot silently redefine what a "capability" or a "view" means.

A recipient is one stable identity for the life of an envelope. Reissuing invitation delivery to that recipient — because a link expired, delivery failed terminally, or an operator asks to resend — never creates a new recipient or a new envelope-recipient graph entry; it produces a new capability for the existing recipient row. Capabilities for one recipient form an append-only lineage: each new capability records the specific predecessor it supersedes, and at most one capability in that lineage is ever live — resolvable, non-revoked, non-expired — at a time. Superseding the old capability and minting the replacement happen atomically; there is no window where two capabilities for the same recipient both resolve.

The first-view evidence recorded in `recipient_viewed_command` and the `recipient.viewed` audit event is immutable and permanently bound to the capability that actually performed that first view. Reissuing a capability never rewrites, re-attributes, or duplicates this evidence, and reissuing is never itself a second view: it is a separate, repeatable operator command with its own audit event. That event follows the same PII- and secret-minimization discipline as every other event in this contract: its public payload may include only the recipient ID, a stable reason code, and timestamps, plus existing non-secret workflow metadata already carried by comparable events where essential; it must never contain raw tokens, capability hashes or other capability identifiers, ciphertext, key IDs, or delivery/outbox IDs. Distinguishing the historical capability that performed the first view from the capabilities that later superseded it is the job of the immutable command receipt and the issuance ledger — both server-side, non-public records — never the public audit payload.

A newly issued capability may be treated as continuing a previously viewed recipient — meaning the browser can proceed toward signing without repeating `POST /api/v1/signing/viewed` side effects — only when the durable issuance ledger proves an unbroken lineage from the historical capability that recorded `recipient_viewed_command` through every intermediate supersession to the capability currently presented. Lineage continuation is never an assumed replay and never silently granted; it must be positively proven from the issuance ledger on every request, not cached or inferred from cookie state alone.

The exact outcome for a presented capability depends on both liveness and lineage, and the atomic reissue slice must not blur together the different failure shapes involved. A token that is not live — its hash matches no current live capability, it is revoked, or it is capability-expired with nothing superseding it — resolves the existing opaque `not_found`, exactly as an unrecognized or non-live hash already does today; that path is unaffected by reissue and stays `not_found`. A live token whose recipient is not yet `viewed` is an ordinary first view or an ordinary idempotency-key replay, unaffected by reissue. A live token whose recipient is already `viewed` and whose lineage back to the capability that recorded `recipient_viewed_command` is proven by the issuance ledger results in continuation: the recipient proceeds without a second `recipient.viewed` event and without the request being recorded as an idempotency-key replay. A live token whose recipient is already `viewed`, where the presented capability genuinely is the current live successor but its lineage to the capability that recorded the view cannot be proven, results in `integrity_error`. This is a new check the atomic reissue slice must add, not a relabeling of today's `not_found` path: today, with no lineage to check at all, a capability that is not the recipient's sole live capability simply fails the live-capability lookup and is `not_found`, and that stays true — the new `integrity_error` branch only ever applies once the presented token has already been confirmed live. The pre-existing `integrity_error` case — a `viewed` recipient with no valid command or audit evidence at all for the very capability presented — is unchanged and remains a separate, same-capability check; it is not the cross-capability lineage check reissue adds.

Lineage continuation is recorded distinctly from idempotency-key replay and must never be conflated with it. Exact-key replay of `POST /api/v1/signing/viewed` remains scoped only to the literal capability and idempotency key that produced the original `recipient.viewed` event and is unaffected by reissue. As established above, the distinction between the capability that actually viewed and the capabilities later reissued lives only in the immutable command receipt and issuance ledger, never in the public `recipient.capability_reissued` payload.

There is exactly one recipient-session cookie per browser; reissue introduces no second cookie or per-tab session, matching the existing `/s/<token>` model. HTTP cookies have no value-conditional delete: a `Set-Cookie` deletion for a given name and path always clears whatever the browser currently has stored under that name, regardless of which token the response-generating request itself read when it decided to delete. With one shared cookie name, a late-arriving denial response for a now-superseded token (H1) can therefore delete a cookie that a different, concurrent exchange of the replacement link (H2) already wrote, purely because of response arrival order — the two requests never coordinate, and the deletion is unconditional at the transport layer no matter how correctly the server-side check that produced it was scoped. The only way to remove this race is for every non-terminal recipient surface to become overwrite-only in the same atomic slice that ships reissue: invalid, unknown, expired, revoked, or superseded tokens, and every `not_found`, `context_mismatch`, `integrity_error`, and `unavailable` response, must emit no `Set-Cookie` deletion at all. An inactive cookie is left inert rather than actively cleared — presenting it still fails closed on durable re-resolution every time regardless of whether it was ever deleted — and it is retired only by its own bounded `maxAge` (the existing capability-expiry/30-day cap) elapsing, or by being wholesale overwritten once its holder completes a genuinely valid `/s` exchange. Visiting a superseded `/s/{oldToken}` link must therefore never delete an existing cookie; only a successful, valid exchange overwrites the same cookie name and path, which is safe because writing a known-good value never depends on first verifying what was previously stored. The reissue operator command itself writes no recipient cookie at all; only a subsequent recipient-initiated `/s` exchange ever does. Because the cookie is shared across tabs rather than scoped to one, a stale tab that has not itself exchanged any link can still observe a live replacement cookie on its very next request purely because a different tab already completed that exchange; that request must lineage-continue exactly as defined above rather than being treated as suspicious.

Terminal recipient responses are decline, approve, and sign; operator void is a separate organization-authorized command that revokes capabilities in the database but never holds or mutates the recipient browser cookie itself. Decline, approve, or sign completion may still deliberately expire or exchange the active session cookie, including the existing cross-name swap to a separate decline-receipt cookie, exactly as it does today. This remains safe only because reissue is defined above to reject already-`declined` and `completed` recipients: a terminal transition and a competing reissue can therefore never be issuing cookies for the same recipient at the same time, so there is no concurrent write for a terminal deletion or exchange to race against. If that precondition is ever relaxed so reissue can target a terminal recipient, every terminal surface must first become overwrite-only in the same way as the non-terminal surfaces above, before that relaxation ships. Likewise, the existing rule that a successful new active link deletes a stale decline-receipt cookie remains sound only for the recipient states where reissue is impossible today; it must not be generalized to any state where a competing reissue could concurrently be minting a live replacement cookie.

Reissue eligibility must not conflate envelope-level terminal expiry with capability-level expiry, which are different things today. An envelope already in its own terminal `expired` state is rejected for reissue exactly like `voided` and `completed`, the same as every other still-deliverable invitation intent. Capability expiry is unrelated: every capability carries its own expiry timestamp, and a recipient whose most recent capability has simply expired while the recipient itself remains `pending` or `viewed` inside a `sent` or `in_progress` envelope is precisely the primary case reissue exists to serve, and must remain eligible. `pending` or `viewed` plus `sent` or `in_progress` is necessary but not sufficient, though: a recipient in a later, not-yet-released routing group is also `pending` with a reserved capability, but that capability was never activated — its durable `recipient.capability_expires_at` is still `NULL` and its outbox row is still `blocked` — precisely because release, not reissue, is what turns a blocked future-routing reservation into a live, expiring link. Reissue therefore additionally requires that the targeted recipient has been released at least once: durable `recipient.capability_expires_at IS NOT NULL`, whether that expiry is now in the future or already in the past, and the invitation it would supersede is not merely a blocked, reserved future-routing intent. A recipient whose group has never been released is rejected without mutation; only the normal routing-release transition performed by approval or signing can make it eligible, never reissue. The full eligibility rule is therefore: the envelope must be `sent` or `in_progress`; the recipient must be `pending` or `viewed`; and the recipient must already have been released, meaning `recipient.capability_expires_at IS NOT NULL` and its current outbox row is not a still-blocked future-routing reservation. Once release has occurred, whether that capability now happens to be still live, capability-expired, or revoked is irrelevant to eligibility and affects only which capability the new one supersedes; a still-`blocked` recipient is never eligible, because minting a new expiry for it would make its link resolvable before its order opens.

The transaction boundary matches the existing decline/void/approve pattern rather than introducing a new one. PostgreSQL locks the envelope row, then the target recipient row, then the recipient's existing outbox row(s), in that stable order inside one transaction, before superseding the old capability, inserting the new capability and a new delivery outbox row, and appending the reissue audit event. D1 performs the same sequence behind one command insert and a rollback-on-failed-predicate trigger, so supersession, new-capability insertion, new-outbox insertion, and audit append either all become visible together or none do. As with decline and void, a `processing` delivery lease observed on the recipient's current outbox row before publication fences the entire reissue with a retryable conflict and no partial write, so a reissue can never race an in-flight provider submission for the capability it is about to supersede. The release predicate above — recipient status, `capability_expires_at IS NOT NULL`, and an outbox row that is not still `blocked` — is rechecked inside this same atomic boundary alongside the lease fence and the capability-supersession CAS, not as a separate earlier check: PostgreSQL rechecks it under the recipient row lock immediately before superseding, and D1's rollback-on-failed-predicate trigger guards it as one of the same predicates. Reissue evaluates that predicate atomically under its own publication boundary: if it observes the recipient still unreleased, it fails closed with no mutation, exactly as above. If a concurrent routing-group release instead commits first, reissue then observes an already-released recipient and may legitimately proceed as an ordinary already-released reissue — the two commands are never interleaved and no execution can publish a reissued live capability before the routing release that made the recipient eligible; each recheck simply sees whichever fully committed state existed first.

Reissue must never overwrite delivery outbox history. Each reissue creates a new outbox row for the new capability rather than mutating or deleting the prior row; delivered and already-permanent-failure evidence on earlier rows remains exactly as retained today. This is required so a future implementation can represent distinct invitation attempts or issuances as an ordered sequence of outbox rows per recipient, not a single mutable slot.

Landing this is one atomic feature slice, not a series of partial merges: an issuance ledger (plus a backfill migration establishing a trivial single-entry lineage for every existing recipient capability), the reissue command itself, the delivery/outbox changes needed to append rather than overwrite, lineage-aware view continuation in the viewed-recording path, the overwrite-only failure-response rule above for every non-terminal surface, and D1/PostgreSQL parity tests must all land together. A partial merge — for example shipping capability supersession without also shipping the overwrite-only rule — would leave the old, now-superseded hash following today's unmodified `not_found` path, whose unmodified deletion response could still race a concurrently exchanged replacement link's cookie write exactly as described above; lineage continuation and the overwrite-only failure responses must land together with the reissue command itself, not as a follow-up.

Acceptance-test contract for a future implementation:

- Reissuing an already-released, `pending`, not-yet-viewed recipient (`recipient.capability_expires_at IS NOT NULL`) mints one new live capability, supersedes the old one, leaves the recipient `pending`, appends one `recipient.capability_reissued` event whose public payload contains only the recipient ID, reason, and timestamps, and makes the old link resolve `not_found`.
- Reissuing a recipient who has already been released at least once (`recipient.capability_expires_at IS NOT NULL`) and whose current capability has simply capability-expired, while the recipient remains `pending` or `viewed` and the envelope remains `sent` or `in_progress`, is accepted; reissuing a recipient inside an envelope-terminal `expired`, `voided`, or `completed` state, or a `declined` or `completed` recipient, is rejected without mutation.
- Reissuing a `pending` recipient in a later, not-yet-released routing group — `recipient.capability_expires_at` still `NULL` and its outbox row still `blocked` — is rejected without mutation regardless of envelope state; only the normal routing-release transition performed by approval or signing can make that recipient eligible, never reissue.
- A routing-group release and a concurrent reissue attempt racing the same recipient never interleave: the D1 trigger and PostgreSQL transaction recheck the release predicate atomically with status, lease, and the capability-supersession CAS; reissue fails closed with no mutation if it observes the recipient still unreleased, and may otherwise proceed as an ordinary already-released reissue if the release fully committed first, but no execution ever publishes a reissued live capability ahead of the routing release itself.
- A live replacement capability presented for an already-`viewed` recipient with intact lineage results in continuation: no second `recipient.viewed` event, and the request is not recorded as an idempotency-key replay.
- A live capability presented for an already-`viewed` recipient whose lineage back to the capability that recorded the view cannot be proven results in `integrity_error`, with no `Set-Cookie` in the response.
- A token that is not live at all (unknown hash, revoked, or capability-expired with nothing superseding it) results in `not_found`, with no `Set-Cookie` in the response; the existing cookie, if any, is left completely untouched.
- Every non-terminal denial or error outcome — `not_found`, `context_mismatch`, `integrity_error`, and `unavailable` — emits no `Set-Cookie` deletion under any circumstance.
- Race ordering: an old-capability request (H1) begins, a concurrent valid replacement-link exchange (H2) completes and sets the live cookie, and H1's denial response arrives after H2's; H1's response carries no `Set-Cookie`, so H2's cookie survives untouched.
- Cross-tab: after one tab exchanges a valid replacement link and the shared cookie is updated to the new live token, a second, stale tab for the same recipient that has not itself exchanged any link observes that same live cookie on its next request and must lineage-continue rather than erroring.
- The reissue operator command's own response never sets or clears any recipient browser cookie.
- Published/replayed decline, approve, and sign retain current terminal cookie expiry/exchange behavior, and tests prove reissue rejects the same completed/declined recipient so no live successor can race it.
- Exact idempotency-key replay of the reissue command itself returns the original receipt without minting a second lineage entry or a second outbox row.
- A `processing` lease on the current outbox row fences a concurrent reissue attempt with a retryable conflict and no partial state.
- D1 and PostgreSQL produce an identical resulting projection — recipient status, live capability, full outbox row history, and audit sequence — for every scenario above.

Non-goals: bulk or multi-recipient reissue in one command; changing a recipient's identity, email, or role (reissue only replaces the capability, never the recipient row it belongs to); retroactively altering or deleting any existing `recipient.viewed` or delivery audit evidence; and any UI, copy, or notification design. Recipient capability reissue is also unrelated to sealing-key rotation (tracked separately, issue #10): rotation re-encrypts existing outbox ciphertext under a new deployment secret without changing which capability is live or minting a new token, and can happen with or without any reissue ever occurring; reissue mints an entirely new capability and token and never re-encrypts or reuses old ciphertext.

## Agent-first contract

The first-party UI calls the same versioned application API available to agents. Core commands are create envelope, add documents, commit draft, add recipients, place fields, send, sign/approve/decline, read status, and export evidence.

Every mutation requires:

- an idempotency key;
- the expected state or repository generation;
- actor type and stable actor ID;
- provenance such as API client, automation run, or user session;
- an optional external ID for reconciliation.

The API will use OpenAPI 3.1, structured validation, RFC 9457 problem responses, cursor pagination, and signed retryable webhooks. Stable events include `draft.revision_created`, `envelope.ready`, `envelope.fields_placed`, `envelope.sent`, `recipient.viewed`, `recipient.signed`, `recipient.declined`, `recipient.approved`, `envelope.completed`, and `envelope.voided`.

## Documents and evidence

DOCX import is a bounded asynchronous conversion: hostile DOCX ZIP/XML → sanitized constrained representation → normalized Markdown commit. The original DOCX is outside Git and follows an explicit retention policy. DOCX export is generated from a specific source commit and remains a transient or retained artifact outside Git.

PDF output is also derived from a pinned Git commit. The product must distinguish a visual electronic signature plus evidence trail from cryptographic PDF certification/PAdES. It must not claim the latter until certificate, timestamping, and long-term validation are implemented and verified.

Audit events are normalized append-only rows with tenant, envelope, sequence, actor, event type, canonical payload, time, previous hash, and event hash. Hash chaining improves evidence but does not make the operator-independent claim “tamper-proof.”

## Localization

Paraglide uses `en` and `ja`, in that order: URL, cookie, then base locale. Human pages have explicit `/en` and `/ja` forms while `/` remains the English base. API, well-known, health, webhook, and agent endpoints are excluded from locale routing. Signing links carry the recipient language chosen by the sender. Language controls use language names, not country flags.

## Open-core enterprise boundary

Always open source:

- audit event capture and evidence hashes;
- authorization and tenancy checks;
- backup, restore, and ordinary audit viewing;
- interoperable API and webhook formats.

Commercial modules:

- offline-capable commercial entitlement validation;
- SAML/SCIM enterprise identity features implemented in d6e-auth and consumed here.

Google Workspace, Microsoft Entra ID, Okta, and other enterprise SSO/SAML handling belongs in d6e-auth. SignKit must not grow a competing identity stack.

## Deployment

`DEPLOY_TARGET` selects `node`, `cloudflare`, or `vercel` at build time. Each target produces a separate artifact; there is no universal runtime build.

Node runs as a non-root user in the supplied multi-stage Docker image. A reverse proxy must preserve the public HTTPS origin used to construct the registered `/auth/callback` URI. Cloudflare uses D1/R2 bindings, `nodejs_compat`, generated binding types, and observability. Vercel compiles in CI but is not supported for production until its issue is complete.

## Primary risks

- AGPL contamination from copying upstream implementation or distinctive assets.
- cross-tenant reads or writes caused by missing organization predicates.
- inconsistent SQL/object pointers during concurrent draft commits.
- Worker exhaustion from large Git archives, DOCX ZIP bombs, PDFs, or fonts.
- leaked recipient links or over-broad agent scopes.
- audit claims stronger than the actual threat model.
- PDF rendering and CJK font differences across runtimes.
- webhook SSRF, DNS rebinding, secret leakage, or uncontrolled retries.
- jurisdiction-dependent electronic-signature requirements.
